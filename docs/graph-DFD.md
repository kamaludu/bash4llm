## Bozza preliminare di Data Flow Diagram (DFD) in formato tabellare.

### 1. Inventario Entità Esterne (External Entities)

| ID | Entità Esterna | Ruolo / Interazione con `bash4llm` |
| :--- | :--- | :--- |
| **E1** | **Utente / Terminale (`CLI`, `stdin`, `/dev/tty`, `stdout`, `stderr`)** | Fornisce argomenti CLI, prompt via `stdin` (testo o JSON), password Vault e API key via `/dev/tty`, selezioni interattive. Riceve output LLM, JSON, streaming SSE, help, diagnostica e log/avvisi. |
| **E2** | **Ambiente OS & Variabili d'Ambiente** | Fornisce `uname`, `date`, `stat`, `id`, variabili d'ambiente (`*_API_KEY`, `BASH4LLM_*`, `CONTENT`, `MODEL`, `SYSTEM_PROMPT`, `THREAD_ID`, `NO_COLOR`, `TERM`, ecc.). |
| **E3** | **API Provider LLM Remoti (`BASH4LLM_PROVIDER_URL`)** | Riceve richieste HTTPS (`POST` payload JSON per chat/streaming, `GET` per elenco modelli/validazione chiave) e restituisce JSON o stream SSE (`data: ...`), più verifica handshake TLS. |
| **E4** | **File Utente Esterni (Input / Output / Extras Src)** | File passati con `-f` o `ARGS`, file batch (`--batch`), percorso salvataggio (`--out`), directory sorgente extras (`--install-extras`). |
| **E5** | **Moduli Esterni & Plugin (`extras`, `local-extras`, `providers`)** | Moduli caricati/eseguiti esternamente: `openssl-helper.sh`, `output-sanitizer.sh`, `session-engine.sh`, `hooks/hook.sh`, provider `vendor`/`local`, `tui-repl.sh`, `gui-py.sh`, `run-all-tests.sh`, `bash4llm-completion.sh`. |

### 2. Inventario Archivi di Dati (Data Stores)

| ID | Data Store | Percorso / Identificativo | Dati Contenuti |
| :--- | :--- | :--- | :--- |
| **DS1** | **Configurazione Core** | `$BASH4LLM_CONFIG_DIR/` (`config`, `provider`, `provider-url`, `model.<prov>`) | Parametri runtime (`MODEL`, `TEMPERATURE`, `MAX_TOKENS`, `FORMAT`, `THRESHOLD`), provider attivo, endpoint URL, modello default per provider. |
| **DS2** | **Catalogo Modelli** | `$BASH4LLM_MODELS_DIR/` (`<prov>.txt`, `models.txt`, `*.b64`) | Elenco testuale dei modelli supportati dal provider (e copia codificata Base64). |
| **DS3** | **UI State & Metadati** | `$BASH4LLM_CONFIG_DIR/ui_state/` (`provider_capabilities.json`, `last_api.json`, `last_history.json`, `threads/index.json`, `threads/<tid>.json`) | Stato capacità provider, telemetria ultima chiamata API, ultimo salvataggio history, indice e metadati/titoli dei thread. |
| **DS4** | **Storico & Thread DB** | `$BASH4LLM_HISTORY_DIR/` (`threads/<SAFE_THREAD_ID>.ndjson`, `*-groq-output-*.txt`) + `thread_cache/<key>.cache` | Conversazioni persistenti in formato NDJSON (`ts`, `role`, `content`, `meta`), cache finestre thread con TTL, file output salvati. |
| **DS5** | **Vault Crittografico & Cache RAM** | `$_VAULT_FILE` (`keys.enc` via `openssl-helper.sh`), `_B4L_RT_CTX`, `BASH4LLM_DECRYPTED_VAULT_JSON`, `BASH4LLM_MODEL_CACHE` | Chiavi API cifrate su disco, chiave/contesto sblocco sessione, JSON chiavi decifrate in RAM, cache normalizzazione modelli. |
| **DS6** | **Template, Docs & Manifest Sicurezza** | `$BASH4LLM_TEMPLATES_DIR/<TEMPLATE>`, `$BASH4LLM_EXTRAS_DIR/docs/` (`core-notes.sh`, `help.txt`), `manifest.sha256`, `.sig`, `official-ed25519.pub` | Testo template con placeholder `{{CONTENT}}`, documentazione codici/help, digest SHA-256 attesi e firma Ed25519 dei moduli. |
| **DS7** | **Area Temporanea & Staging Runtime** | `$RUN_TMPDIR/` (`payload*`, `resp.*`, `err.log`, `curl_hdr`, `thread-*-messages.json`, `staged.*`, `provdump.*`) & `$BASH4LLM_RATES_DIR/<tid>/` | Payload JSON/Base64, header HTTP con Bearer token, risposte grezze/chunk SSE, log errori temporanei, copie staging anti-TOCTOU, file timestamp per rate-limit. |
| **DS8** | **File di Log Applicativo** | `$BASH4LLM_LOG` | Righe di log timestampate (`INFO`, `INFO_USER`, `WARN`, `ERROR`, `SECURITY`). |

*Ecco un metodo pratico in due fasi — prima per **verificare e validare** le tabelle, poi per **sfruttarle concretamente** sullo sviluppo, sicurezza e manutenzione di `bash4llm`.*

### Fase 1: Come controllare e validare le tabelle

1. **Unisci e testa l'integrità strutturale in un foglio di calcolo (o Markdown/CSV)**
   * Controlla che ogni riga abbia esattamente 9 colonne e che gli ID scorrano senza salti da `DF-001` a `DF-162`.
   * Se importi tutto in LibreOffice Calc / Excel / Google Sheets (o in Obsidian/Notion), usa i filtri sulle colonne `Sorgente (Da)` e `Destinazione (A)` per verificare che i codici (`E1..E5`, `DS1..DS8`, `P1..P9`) siano coerenti.

2. **Controllo incrociato "Lettori vs Scrittori" sui Data Store**
   * Filtra la colonna `Destinazione` e `Sorgente` per ogni `DS`: ogni archivio dovrebbe avere almeno un processo che ci scrive e almeno uno che lo legge.
   * **Esempio pratico emerso su `bash4llm`:** noterai che `manifest_create`, `manifest_add_part` e `manifest_read` (`DF-097..099`) e `_locked_history_save` (`DF-104`) scrivono/leggono file ma non hanno chiamanti nel flusso principale (`CORE_PROVIDER_PIPELINE_EXEC`). Questo controllo ti conferma subito quali funzioni sono **API di libreria esportate** per gli script esterni (quando usi `BASH4LLM_SOURCE_ONLY=1`) rispetto a quelle usate dal core.

3. **Verifica a campione sui "confini di fiducia" (Trust Boundaries)**
   * Non serve rileggere tutte le 162 righe riga per riga: controlla sul codice sorgente almeno i flussi che attraversano confini esterni:
     * **Input esterni -> RAM/Temp:** `DF-020` (`read_secure_input`), `DF-127` (`stdin` JSON con `api_key`), `DF-128..130` (file utente e template).
     * **Moduli esterni -> Core:** `DF-034` (`openssl-helper.sh`), `DF-062..063` (provider esterni), `DF-101..102` (`hook.sh`), `DF-120` (`session-engine.sh`).
     * **Segreti -> Rete/Log:** `DF-057..058` -> `DF-125..126` (`curl_hdr`).

### Fase 2: Come utilizzarle in pratica

Un DFD da 162 righe è troppo denso per essere letto tutto d'un fiato come un disegno unico, ma diventa potentissimo se lo usi come **database interrogabile**:

#### 1. Audit di Sicurezza & Threat Modeling (es. modello STRIDE)
Puoi filtrare le tabelle per tracciare il ciclo di vita di ogni dato sensibile:
* **Tracciamento segreti (`API Key` e Vault):** segui il percorso `DF-057/058` → `DF-125` → `DF-126` (e `DF-127` per `stdin` JSON). Verifica che nessuna freccia porti `GROQ_API_KEY`, `_B4L_RT_CTX` o il contenuto di `curl_hdr` verso `DS8 ($BASH4LLM_LOG)`, `DS3 (ui_state)` o `E1 (stderr)` in chiaro (es. `DF-060` maschera la chiave prima di stamparla, `DF-108` redige `token|key|secret` prima di scrivere nel thread).
* **Audit Logging (`P2` / `DS8`):** filtrando `Destinazione = P2` o `DS8` vedi in un colpo solo *tutto* ciò che finisce nei log e su `stderr`, utile per assicurarti che nessun contenuto di prompt utente o payload sensibile venga loggato per sbaglio fuori da `DEBUG=1`.

#### 2. Analisi d'Impatto prima di una modifica (Change Impact Analysis)
Quando vuoi modificare un formato dati o un percorso file, filtra il nome della variabile o del file nella tabella per vedere subito cosa rompi:
* Esempio: vuoi cambiare lo schema di `ui_state` (`DS3`) o di `BUILD_MESSAGES_FILE` (`DS7`)? Filtrando quel nome vedrai tutte le righe coinvolte (es. `DF-050`, `DF-064`, `DF-096`, `DF-109..111`, `DF-114`, `DF-116`, `DF-140`, `DF-142`) senza rischiare di dimenticare un punto nascosto nello script.

#### 3. Refactoring e riduzione duplicazioni
Guardando i flussi per blocco noti subito dove lo script ripete pipeline dati quasi identiche:
* Esempio evidente in **Blocco D**: la sequenza *"carica finestra thread → costruisci payload → check API key → chiama API → append `user` e `assistant` su thread"* è replicata in tre punti distinti (`--batch` `DF-151..152`, streaming `DF-154..156`, classico `DF-158..161`). Il DFD ti mostra esattamente quali dati entrano ed escono da quella sequenza se volessi estrarla in una funzione comune.

#### 4. Piano di Test (`run-all-tests.sh`)
Ogni riga `DF-xxx` rappresenta una trasformazione o un ramo di errore reale:
* Puoi usare i flussi come **checklist di copertura test**: per esempio verificare di avere test dedicati per `DF-102` (whitelist hook `TRANSFORMED_PAYLOAD`/`FALLBACK_PAYLOAD`), `DF-127` (`stdin` JSON con `api_key`), `DF-145..147` (`detect_empty_edge_case` e `diagnostic:true`), `DF-150` (salvataggio automatico oltre `THRESHOLD`).

#### 5. Creazione di diagrammi visivi mirati (Mermaid / Draw.io)
Invece di disegnare 162 flussi in un unico grafico illeggibile, estrai **viste tematiche** da 10–15 righe ciascuna:
* *Vista 1:* Solo pipeline richiesta/risposta (`DF-127..150`)
* *Vista 2:* Solo ciclo vita Thread & Cache (`DF-100`, `DF-109..123`, `DF-156`, `DF-160..161`)
* *Vista 3:* Solo caricamento sicuro moduli & Vault (`DF-025..035`, `DF-057..064`, `DF-077`, `DF-101..102`, `DF-120`)
