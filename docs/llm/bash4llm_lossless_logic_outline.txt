SPECIFICA DELL'ARCHITETTURA E DELLA LOGICA DI BASH4LLM⁺ (v2.8.0)

Questo documento descrive in modo completo e senza perdita di informazioni la
logica, le variabili, le funzioni e i blocchi strutturali del sistema Bash4LLM⁺,
suddivisi secondo le cinque macro-sezioni originarie allineate alla versione
stabile 2.8.0.

1. PRECORE_BOOT

VARIABILI

  - SCRIPT_NAME: Nome identificativo del programma (impostato a "bash4llm").
  - SCRIPT_VERSION: Versione corrente del software (impostata a "2.8.0").
  - SCRIPT_DATE: Data di rilascio dello script (impostata a "2026-07-25").
  - BASH4LLM_PLAT_ANDROID: Flag di ambiente (valore 1 o 0) impostato su
    bootstrap indicante se il runtime è eseguito sotto ambiente Android/Termux.
  - BASH4LLM_PLAT_MACOS: Flag di ambiente (valore 1 o 0) impostato su bootstrap
    indicante se il runtime è eseguito sotto sistema macOS/Darwin.
  - BASH4LLM_PLAT_WSL: Flag di ambiente (valore 1 o 0) impostato su bootstrap
    indicante se il runtime è eseguito sotto Windows Subsystem for Linux (WSL).
  - BASH4LLM_PLAT_CYGWIN: Flag di ambiente (valore 1 o 0) impostato su bootstrap
    indicante se l'esecuzione avviene sotto ambienti Windows compatibili Cygwin,
    MSYS2 o MinGW.
  - BASH4LLM_PLAT_BSD: Flag di ambiente (valore 1 o 0) impostato su bootstrap
    indicante se l'esecuzione avviene sotto sistemi FreeBSD, OpenBSD, NetBSD o
    DragonFly.
  - BASH4LLM_PLAT_LINUX: Flag di ambiente (valore 1 o 0) impostato su bootstrap
    indicante se l'esecuzione avviene sotto ambiente Linux generico o WSL.
  - BASH4LLM_KEY_MANUAL_PROMPT: Flag di stato interno (valore 1 o 0) per
    tracciare se una chiave API è stata inserita manualmente dall'utente via
    prompt interattivo TTY, con hard reset iniziale a 0 per prevenire leakage di
    variabili d'ambiente.
  - BASH4LLM_MODEL_CACHE: Array associativo interno adibito ad archiviare in
    memoria i nomi dei modelli normalizzati per velocizzare le esecuzioni
    successive e bypassare sotto-shell o regex ripetute.
  - C_LOGO: Sequenza di escape ANSI per lo stile grafico del logo
    dell'applicazione (sfondo verde, testo bianco in grassetto), disattivata in
    modalità NO_COLOR o terminale dumb.
  - C_BANNER: Sequenza di escape ANSI per il banner dell'applicazione (sfondo
    blu, testo bianco in grassetto), disattivata in modalità NO_COLOR o
    terminale dumb.
  - C_RST: Sequenza di escape ANSI di reset per ripristinare gli stili e i
    colori predefiniti del terminale.
  - C_BOLD, C_NOBOLD: Sequenze di escape ANSI per attivare e disattivare la
    formattazione in grassetto del testo.
  - C_UNDERLINE, C_NOUNDERLINE: Sequenze di escape ANSI per attivare e
    disattivare la sottolineatura del testo.
  - C_BLACK, C_RED, C_GREEN, C_YELLOW, C_BLUE, C_MAGENTA, C_CYAN, C_WHITE:
    Sequenze di escape ANSI per i colori del testo in modalità normale.
  - C_BBLACK, C_BRED, C_BGREEN, C_BYELLOW, C_BBLUE, C_BMAGENTA, C_BCYAN,
    C_BWHITE: Sequenze di escape ANSI per i colori del testo in modalità ad alta
    intensità o grassetto.
  - BG_BLACK, BG_RED, BG_GREEN, BG_YELLOW, BG_BLUE, BG_MAGENTA, BG_CYAN,
    BG_WHITE: Sequenze di escape ANSI per i colori di sfondo del terminale.
  - BASH4LLM_ERR_NO_API_KEY: Costante numerica di errore (valore 10) associata
    alla mancanza di una chiave API.
  - BASH4LLM_ERR_BAD_MODEL: Costante numerica di errore (valore 11) associata
    alla richiesta di un modello non valido o non supportato.
  - BASH4LLM_ERR_CURL_FAILED: Costante numerica di errore (valore 12) associata
    al fallimento della chiamata di rete curl.
  - BASH4LLM_ERR_NO_PROMPT: Costante numerica di errore (valore 14) associata
    alla mancanza di un prompt di input.
  - BASH4LLM_ERR_TMP: Costante numerica di errore (valore 15) associata a
    problemi del file-system temporaneo, permessi non validi o gestione dei file
    di lock.
  - BASH4LLM_ERR_API: Costante numerica di errore (valore 16) associata a
    risposte d'errore o codici HTTP non validi restituiti dal provider API.
  - BASH4LLM_ERR_SEC: Costante numerica di errore (valore 17) associata a
    violazioni della policy di sicurezza, permessi errati sul file-system o
    fallimento della verifica di integrità SHA-256 dei moduli.
  - BASH4LLMERR_NO_API_KEY: Mappatura alias diretta del valore di
    BASH4LLM_ERR_NO_API_KEY con notazione ad underscore.
  - BASH4LLMERR_BAD_MODEL: Mappatura alias diretta del valore di
    BASH4LLM_ERR_BAD_MODEL con notazione ad underscore.
  - BASH4LLMERR_CURL_FAILED: Mappatura alias diretta del valore di
    BASH4LLM_ERR_CURL_FAILED con notazione ad underscore.
  - BASH4LLMERR_NO_PROMPT: Mappatura alias diretta del valore di
    BASH4LLM_ERR_NO_PROMPT con notazione ad underscore.
  - BASH4LLMERR_TMP: Mappatura alias diretta del valore di BASH4LLM_ERR_TMP con
    notazione ad underscore.
  - BASH4LLMERR_API: Mappatura alias diretta del valore di BASH4LLM_ERR_API con
    notazione ad underscore.
  - BASH4LLMERR_SEC: Mappatura alias diretta del valore di BASH4LLM_ERR_SEC con
    notazione ad underscore.
  - DEBUG: Flag di configurazione per l'output di tracciamento dello sviluppo.
    Eredita il valore di ambiente ${DEBUG} o ${BASH4LLM_DEBUG}, o viene
    impostato su 0 (disattivo).
  - BASH4LLM_LOG: Percorso assoluto o relativo del file in cui registrare i log
    di tracciamento. Eredita ${BASH4LLM_LOG} (vuoto se disattivato).
  - SCRIPTDIR: Percorso assoluto della directory contenente lo script corrente,
    risolto dinamicamente tramite la funzione resolve_script_dir.
  - BASH4LLM_DIR: Directory principale di installazione dei dati e delle
    configurazioni di Bash4LLM⁺. Dichiarata dall'ambiente o derivata da
    SCRIPTDIR/bash4llm.d.
  - BASH4LLM_CONFIG_DIR: Directory dei file di configurazione utente
    persistenti. Impostata a BASH4LLM_CONFIG_DIR di ambiente o posizionata sotto
    $BASH4LLM_DIR/config.
  - BASH4LLM_MODELS_DIR: Directory dei file relativi ai modelli supportati.
    Impostata a BASH4LLM_MODELS_DIR di ambiente o posizionata sotto
    $BASH4LLM_DIR/models.
  - BASH4LLM_TEMPLATES_DIR: Directory contenente i file dei modelli di template.
    Impostata a BASH4LLM_TEMPLATES_DIR di ambiente o posizionata sotto
    $BASH4LLM_DIR/templates.
  - BASH4LLM_HISTORY_DIR: Directory contenente lo storico e i log delle
    interazioni dello script. Impostata a BASH4LLM_HISTORY_DIR di ambiente o
    posizionata sotto $BASH4LLM_DIR/history.
  - BASH4LLM_TMPDIR: Directory radice per l'allocazione dei dati temporanei di
    Bash4LLM⁺. Impostata a BASH4LLM_TMPDIR di ambiente o posizionata sotto
    $BASH4LLM_DIR/tmp.
  - BASH4LLM_RUN_DIR: Directory isolata per i file di stato ed esecuzione del
    runtime. Impostata a BASH4LLM_RUN_DIR di ambiente o posizionata sotto
    $BASH4LLM_DIR/var/run.
  - BASH4LLM_LOCKS_DIR: Directory dedicata alla memorizzazione isolata dei file
    di lock concorrenziali per prevenire race conditions. Impostata sotto
    $BASH4LLM_RUN_DIR/locks.
  - CANONICAL_EXTRAS_DIR: Percorso della directory canonica delle estensioni,
    calcolato rimuovendo la barra finale da BASH4LLM_DIR e annettendo /extras.
  - LEGACY_EXTRAS_DIR: Percorso storico di fallback delle estensioni, relativo
    alla cartella dello script (SCRIPTDIR/extras).
  - BASH4LLM_EXTRAS_DIR: Directory attiva per l'accesso alle risorse aggiuntive
    dello script (assegnata a CANONICAL_EXTRAS_DIR).
  - PROVIDERS_DIR: Percorso assoluto o relativo dei moduli esterni dei provider
    (impostato su PROVIDERS_DIR di ambiente o localizzato sotto
    $BASH4LLM_EXTRAS_DIR/providers).
  - THREAD_DIR: Directory dedicata alla registrazione dei log storici NDJSON dei
    thread (posizionata in $BASH4LLM_HISTORY_DIR/threads).
  - TMPDIR: Override dell'ambiente di sistema forzato su BASH4LLM_TMPDIR per
    garantire l'isolamento locale e sicuro di cURL e dei file provvisori.
  - BASH4LLM_RATES_DIR: Directory isolata per la memorizzazione dei marcatori
    transazionali del rate limiting locale (posizionata in
    $BASH4LLM_TMPDIR/rates).
  - BASH4LLM_VAULT_ENABLED: Variabile di controllo per l'abilitazione (1) o
    disattivazione (0) del Key Vault OpenSSL. Prelevata dall'ambiente o
    impostata di default a 1.
  - _BASH4LLM_OPENSSL_HELPER: Percorso completo del modulo di ausilio
    crittografico OpenSSL ($BASH4LLM_EXTRAS_DIR/security/openssl-helper.sh).
  - BASH4LLM_OPENSSL_ACTIVE: Flag booleano interno indicante se
    openssl-helper.sh è stato validato tramite integrità SHA-256 e caricato con
    successo nel runtime (valore 1 o 0).
  - MODELS_FILE: File di testo locale in cui memorizzare la lista dei modelli
    recuperati per il provider attivo, sincronizzato tramite
    sync_models_file_path.
  - MAX_MODELS: Limite numerico massimo di modelli importabili o gestibili
    localmente. Eredita ${MAX_MODELS} o adotta il valore di default di 200.
  - PROVIDER_FILE: Percorso del file che persiste l'ultimo provider configurato
    dall'utente, determinato tramite canonical_provider_file.
  - MODELS_LOCK: Percorso del file di lock di sincronizzazione per l'accesso ai
    modelli, posizionato sotto $BASH4LLM_LOCKS_DIR/models.lock.
  - HISTORY_LOCK: Percorso del file di lock per l'accesso concorrente ai log di
    storico e sessione, posizionato sotto $BASH4LLM_HISTORY_DIR/history.lock.
  - TMP_LOCK: Percorso del file di lock esclusivo per la gestione sicura della
    directory temporanea dello script, posizionato sotto
    $BASH4LLM_LOCKS_DIR/tmp.lock.
  - BASH4LLM_LOCK_TIMEOUT_TMP: Timeout massimo di attesa espresso in secondi per
    acquisire il lock temporaneo (eredita BASH4LLM_LOCK_TIMEOUT_TMP o
    imposta 10).
  - BASH4LLM_LOCK_TIMEOUT_MODELS: Timeout in secondi per acquisire il lock sui
    modelli (eredita BASH4LLM_LOCK_TIMEOUT_MODELS o imposta 10).
  - BASH4LLM_LOCK_TIMEOUT_HISTORY: Timeout in secondi per acquisire il lock
    sullo storico dei messaggi e dei thread (eredita
    BASH4LLM_LOCK_TIMEOUT_HISTORY o imposta 10).

FUNZIONI

  - resolve_script_dir

      - Scopo: Identifica la cartella reale in cui risiede lo script in
        esecuzione, tracciando in modo sicuro i collegamenti simbolici sul
        file-system.
      - Input: Nessuno (analizza la variabile speciale ${BASH_SOURCE[0]}).
      - Output: Restituisce su standard output il percorso assoluto normalizzato
        della directory.
      - Side-effects: Nessuno.
      - Dipendenze: Comandi readlink, dirname, cd, pwd, printf.

  - safe_mkdir

      - Scopo: Crea in sicurezza una directory con i permessi specificati,
        verificando che non coincida con un collegamento simbolico (mitigazione
        symlink attack).
      - Input: $1 (directory), $2 (opzionale: permessi ottali, default 700).
      - Output: Stato 0 o arresto immediato con codice d'uscita 15
        (BASH4LLM_ERR_TMP) se fallisce la creazione o se viene rilevato un
        symlink.
      - Side-effects: Verifica symlink, creazione directory, modifica permessi
        tramite chmod.
      - Dipendenze: Comandi mkdir, chmod, printf.

  - check_required_arg

      - Scopo: Convalida la presenza del parametro CLI obbligatorio richiesto da
        un'opzione, verificando la prossimità del limite posizionale degli
        argomenti.
      - Input: $1 (opzione indagata), $2 (conteggio argomenti residui).
      - Output: Stato 0 o arresto con codice 15 (BASH4LLM_ERR_TMP).
      - Side-effects: Emissione di un log di errore su stderr.
      - Dipendenze: Funzione log_error.

  - canonical_config_dir

      - Scopo: Normalizza il percorso della directory di configurazione
        rimuovendo eventuali barre finali ridondanti.
      - Input: Nessuno (analizza $BASH4LLM_CONFIG_DIR).
      - Output: Restituisce il percorso canonico su standard output.
      - Side-effects: Nessuno.
      - Dipendenze: Comando printf.

  - canonical_provider_file

      - Scopo: Genera il percorso canonico del file di persistenza del provider
        selezionato.
      - Input: Nessuno.
      - Output: Restituisce su standard output il percorso del file /provider
        sotto la directory canonica di configurazione.
      - Side-effects: Richiama internamente canonical_config_dir.
      - Dipendenze: Comando printf, funzione canonical_config_dir.

  - canonical_model_file

      - Scopo: Genera il percorso del file in cui memorizzare il modello
        predefinito associato a un determinato provider.
      - Input: $1 (nome identificativo del provider).
      - Output: Restituisce su standard output il percorso del file formato
        /model.<provider> posizionato nella directory canonica di
        configurazione.
      - Side-effects: Richiama internamente canonical_config_dir.
      - Dipendenze: Comando printf, funzione canonical_config_dir.

  - canonical_provider_url_file

      - Scopo: Genera il percorso canonico del file contenente l'endpoint o URL
        API specifico del provider attivo.
      - Input: Nessuno.
      - Output: Restituisce su standard output il percorso del file
        /provider-url posizionato nella directory canonica di configurazione.
      - Side-effects: Richiama o simula la logica di canonical_config_dir.
      - Dipendenze: Comandi type, printf, funzione canonical_config_dir.

  - trim_space

      - Scopo: Rimuove spazi e tabulazioni iniziali e finali tramite costrutti
        di scomposizione nativi della shell (senza fork di processi esterni).
      - Input: $1 (stringa da ripulire).
      - Output: Stringa pulita inviata su standard output.
      - Side-effects: Nessuno.
      - Dipendenze: Comando printf.

  - sync_models_file_path

      - Scopo: Sincronizza il percorso globale di MODELS_FILE basandosi sul
        provider attivo, forzando una sanitizzazione protettiva contro directory
        traversal che esclude caratteri non alfanumerici (eccetto trattino e
        trattino basso).
      - Input: $1 (opzionale: nome provider, default $PROVIDER o "groq").
      - Output: Esporta la variabile MODELS_FILE nell'ambiente di esecuzione.
      - Side-effects: Modifica della variabile d'ambiente globale MODELS_FILE.
      - Dipendenze: Comando export.

  - _normalize_model_name

      - Scopo: Esegue la normalizzazione dei nomi dei modelli rimuovendo spazi,
        ritorni a capo ed i prefissi models/ e nomi provider. Per ottimizzare il
        runtime, conserva i risultati in un array associativo di cache in
        memoria (BASH4LLM_MODEL_CACHE).
      - Input: $1 (nome modello).
      - Output: Nome del modello normalizzato e filtrato da whitelist su
        standard output.
      - Side-effects: Popola l'array associativo BASH4LLM_MODEL_CACHE.
      - Dipendenze: Funzioni normalize_model_<provider> se definite.

  - is_truthy

      - Scopo: Valuta se il parametro testuale in ingresso rappresenta un valore
        di veridicità affermativo logico.
      - Input: $1 (stringa da valutare).
      - Output: Ritorna stato 0 (vero) se il parametro corrisponde a 1, true,
        TRUE, True, yes, YES o Yes. In tutti gli altri casi ritorna 1 (falso).
      - Side-effects: Nessuno.
      - Dipendenze: Nessuna.

  - _extract_notes_section

      - Scopo: Estrae sezioni testuali letterali (senza esecuzione di codice)
        dal file di documentazione core-notes.sh.
      - Input: $1 (titolo della sezione target).
      - Output: Righe estratte stampate su standard output o stato 1 se il file
        è assente.
      - Side-effects: Lettura da file-system.
      - Dipendenze: Comando awk.

  - log_prefix

      - Scopo: Restituisce il prefisso di intestazione unificato per i log dello
        script.
      - Input: Nessuno.
      - Output: Restituisce su standard output la stringa formattata bash4llm: .
      - Side-effects: Nessuno.
      - Dipendenze: Comando printf.

  - log_info

      - Scopo: Traccia e visualizza i messaggi informativi.
      - Input: $1 (codice categoria/modulo, default "INFO"), $2 (corpo del
        messaggio).
      - Output: Scrive il messaggio formattato su stderr se $DEBUG è attivo. Se
        $BASH4LLM_LOG è valorizzato, appende il record con timestamp UTC e
        categoria nel file di destinazione.
      - Side-effects: Scrittura su console e file-system.
      - Dipendenze: Funzione log_prefix, comandi date, printf.

  - log_warn

      - Scopo: Traccia e visualizza a schermo i messaggi di avvertimento non
        critici.
      - Input: $1 (codice modulo, default "WARN"), $2 (corpo del messaggio).
      - Output: Scrive il messaggio su stderr. Se abilitato il log, appende il
        tracciamento nel file $BASH4LLM_LOG.
      - Side-effects: Scrittura su stderr e file-system.
      - Dipendenze: Funzione log_prefix, comandi date, printf.

  - log_error

      - Scopo: Registra ed evidenzia gli errori critici.
      - Input: $1 (codice modulo, default "ERROR"), $2 (corpo del messaggio).
      - Output: Scrive l'errore su stderr. Se abilitato il log, appende il
        tracciamento nel file $BASH4LLM_LOG.
      - Side-effects: Scrittura su stderr e file-system.
      - Dipendenze: Funzione log_prefix, comandi date, printf.

  - log_info_user

      - Scopo: Registra messaggi informativi di esecuzione destinati all'utente
        (non silenziati da QUIET) su stderr e file di log.
      - Input: $1 (modulo), $2 (messaggio).
      - Output: Stampa formattata su stderr se QUIET=0 e scrittura su file log.
      - Side-effects: Scrittura su stderr e file-system.
      - Dipendenze: Funzione log_prefix, comandi date, printf.

  - dbg

      - Scopo: Visualizza messaggi di diagnostica rapida su stderr se il debug è
        attivo.
      - Input: Argomenti testuali liberi da stampare ($*).
      - Output: Righe di testo inviate a stderr.
      - Side-effects: Scrittura su stderr.
      - Dipendenze: Comando printf.

  - read_secure_input

      - Scopo: Acquisisce in modo sicuro input sensibili (es. chiavi API,
        password) disabilitando l'echo del terminale.
      - Input: $1 (nome della variabile target), $2 (messaggio prompt), $3
        (lunghezza minima richiesta, default 0), $4 (opzionale: verifica
        inserimento).
      - Output: Ritorna stato 0 ed assegna l'input pulito alla variabile target
        tramite printf -v. Ritorna 1 in caso di errore o lunghezza
        insufficiente.
      - Side-effects: Disabilita e ripristina l'echo del terminale tramite stty
        -echo / stty echo su /dev/tty prima di mostrare il prompt, imposta trap
        temporanea per ripristinare il terminale su interruzione.
      - Dipendenze: Comandi stty, trap, printf, read.

  - validate_file_input

      - Scopo: Esegue la convalida di sicurezza di un file di input per scopi
        transazionali, verificando l'esistenza, la leggibilità, che la
        dimensione non sia zero e l'assenza di byte nulli o controlli C0 non
        consentiti (tranne tab, CR, LF).
      - Input: $1 (percorso del file).
      - Output: Codici stato: 0 (valido), 1 (percorso vuoto), 2 (file non
        trovato o non leggibile), 3 (file vuoto a 0 byte), 4 (presenza di byte
        nulli o caratteri di controllo non ammessi).
      - Side-effects: Lettura del file.
      - Dipendenze: Funzione file_size, comandi tr, wc, LC_ALL=C.

  - _get_perm_string

      - Scopo: Restituisce la stringa dei permessi di un file/directory in
        notazione simbolica (es. -rwxr-xr-x), unificando le differenze tra
        Linux, macOS e BSD.
      - Input: $1 (percorso del file o directory).
      - Output: Stringa dei permessi stampata su standard output.
      - Side-effects: Nessuno.
      - Dipendenze: Comando stat con flag specifici di piattaforma.

  - _get_owner

      - Scopo: Restituisce il nome dell'utente proprietario di un file o
        directory in modo portabile.
      - Input: $1 (percorso).
      - Output: Nome dell'owner su standard output.
      - Side-effects: Nessuno.
      - Dipendenze: Comando stat con flag specifici di piattaforma.

  - validate_path_security

      - Scopo: Convalida la sicurezza di un percorso verificando che il file e
        la directory genitrice non siano symlink, siano di proprietà dell'utente
        corrente e non siano scrivibili da gruppo o altri (group/world
        writable).
      - Input: $1 (percorso del file target).
      - Output: Ritorna stato 0 se sicuro, 1 se vengono rilevate violazioni di
        sicurezza.
      - Side-effects: Scrittura di log di errore o avvertimento.
      - Dipendenze: Funzioni _get_owner, _get_perm_string, log_error, log_warn,
        is_truthy, comandi dirname, id, awk.

  - _core_sha256

      - Scopo: Calcola l'hash crittografico SHA-256 digest di un file
        utilizzando i binari di sistema nativi indipendenti dal modulo helper
        OpenSSL.
      - Input: $1 (percorso del file).
      - Output: Digest SHA-256 esadecimale stampato su standard output, oppure
        ritorna 1 in caso di fallimento.
      - Side-effects: Lettura del file.
      - Dipendenze: Comandi sha256sum, openssl, shasum, awk.

  - verify_module_integrity

      - Scopo: Verifica la sicurezza dei permessi del percorso e l'integrità
        crittografica SHA-256 di un modulo o script rispetto al file manifesto
        di integrità (extras/manifest.sha256).
      - Input: $1 (percorso del file target).
      - Output: Ritorna stato 0 se l'integrità è verificata o se il file non è
        presente nel manifesto ma il percorso è sicuro. Ritorna BASH4LLM_ERR_SEC
        (17) in caso di manomissione o violazione di sicurezza.
      - Side-effects: Calcolo hash SHA-256 e logging di errore in caso di
        mismatch.
      - Dipendenze: Funzioni validate_path_security, _core_sha256, log_error,
        log_info, comandi awk, basename, dirname, cd, pwd.

  - ensure_api_key_for_provider

      - Scopo: Recupera la chiave API per il provider selezionato seguendo la
        gerarchia di sicurezza: 1) Key Vault OpenSSL decrittografato in memoria
        se presente; 2) Variabile d'ambiente (se BASH4LLM_REQUIRE_VAULT=0); 3)
        Inserimento manuale interattivo via read_secure_input.
      - Input: $1 (nome del provider).
      - Output: Ritorna stato 0 ed esporta la chiave API nell'ambiente. Ritorna
        BASH4LLM_ERR_NO_API_KEY o BASH4LLM_ERR_SEC se la chiave manca o se vi è
        una violazione di policy.
      - Side-effects: Lettura da Vault, esportazione variabili d'ambiente
        (GROQ_API_KEY, ecc.), prompt TTY.
      - Dipendenze: Funzioni provider_api_env_var_name, vault_exists,
        vault_load_keys, log_info_user, log_warn, log_error, read_secure_input,
        is_truthy, comandi jq, export.

  - enforce_network_policy

      - Scopo: Valuta se lo stato corrente del runtime permette l'esecuzione di
        richieste di rete reali o se queste devono essere bloccate.
      - Input: Nessuno (analizza $DRY_RUN, $BASH4LLM_SKIP_NETWORK,
        $BASH4LLM_ENFORCE_NO_NETWORK_IF_QUIET, $QUIET).
      - Output: Ritorna stato 1 se le connessioni esterne sono bloccate (o in
        simulazione dry-run), 0 se autorizzate.

2. PRECORE_RUN

VARIABILI

  - BASH4LLM_ROTATE_HISTORY: Flag di configurazione (valore 1 o 0, default 0)
    per attivare la rotazione automatica periodica dello storico delle
    interazioni.
  - BASH4LLM_HISTORY_MAX_FILES: Soglia numerica massima di file memorizzabili
    nello storico delle risposte (default 100). Superata la soglia, i file più
    vecchi vengono rimossi.
  - BASH4LLM_HISTORY_MAX_BYTES: Soglia massima espressa in byte del peso
    cumulativo di tutti i file storici archiviati (default 104857600,
    equivalente a 100MB).
  - BASH4LLM_HISTORY_KEEP_DAYS: Limite di tempo espresso in giorni per la
    conservazione dei log e dello storico (default 90). I file più vecchi della
    soglia vengono eliminati.
  - THREAD_CACHE_DIR: Directory destinata a contenere la cache temporanea dei
    dati e dei messaggi dei thread attivi (localizzata sotto la directory di
    configurazione utente, alla voce thread_cache/).
  - CONTENT: Prompt testuale primario dell'utente.
  - PROVIDER: Identificatore del provider API attivo (default "groq").
  - JSON_INPUT: Input strutturato in formato JSON fornito dall'utente per
    definire direttamente i messaggi o le proprietà della richiesta.
  - THREAD_ID: Identificatore alfanumerico del thread di chat corrente,
    trasformato nell'hash anonimizzato SAFE_THREAD_ID per la persistenza del
    contesto multi-turno.
  - SAFE_THREAD_ID: Identificatore anonimizzato crittograficamente in memoria
    (digest esadecimale) per garantire che identificativi o PII dell'utente non
    vengano mai scritti in chiaro sul disco.
  - THREAD_WINDOW: Numero massimo di messaggi storici da estrarre e accodare dal
    log NDJSON del thread per comporre la finestra di contesto della chat.
  - TEMPLATE: Nome identificativo del file di template da applicare per
    formattare o arricchire il prompt dell'utente prima dell'invio.
  - BATCH_FILE: Percorso di un file contenente una serie ordinata di prompt (uno
    per riga) da elaborare in sequenza batch.
  - CHAT_MODE: Flag booleano (valore 1 o 0, default 0) che abilita l'interfaccia
    interattiva TUI REPL da terminale.
  - SET_DEFAULT_MODEL: Nome del modello da memorizzare e configurare come scelta
    predefinita persistente per il provider attivo.
  - REFRESH_MODELS: Flag booleano (valore 1 o 0, default 0) per forzare
    l'allineamento e l'interrogazione delle API esterne al fine di aggiornare la
    lista locale dei modelli supportati.
  - LIST_MODELS: Flag booleano (valore 1 o 0, default 0) per visualizzare a
    schermo l'elenco dei modelli disponibili.
  - FORCE_SAVE_MODE: Regola il salvataggio dell'output testuale generato sul
    disco ("save" forza il salvataggio, "nosave" lo disabilita, 0 o vuoto adotta
    il comportamento standard basato sulla soglia).
  - OUT_PATH: Percorso del file o della directory personalizzata in cui
    archiviare i risultati restituiti dalle API.
  - SYSTEM_PROMPT: Prompt di sistema personalizzato utilizzato per istruire o
    condizionare il comportamento e il tono del modello LLM.
  - TEMPERATURE / TURE: Valore numerico decimale che regola la temperatura di
    campionamento delle risposte delle API (eredita ${TEMPERATURE}, ${TURE} o
    adotta 1.0). Sincronizzato con TURE.
  - MAX_TOKENS: Limite di token generabili nella risposta (default 4096).
  - MODEL: Nome identificativo del modello LLM richiesto per l'elaborazione
    (ereditato o impostato via CLI o config).
  - AUTO_POLICY: Politica adottata per la selezione automatica del modello di
    fallback in assenza di un modello espresso esplicitamente dall'utente
    (default "preferred").
  - QUIET: Flag booleano (valore 1 o 0, default 0) per inibire i messaggi
    informativi e limitare l'output ai soli risultati o errori bloccanti.
  - DRY_RUN: Flag booleano (valore 1 o 0, default 0) per simulare l'esecuzione
    ed escludere l'invio reale di chiamate di rete esterne.
  - STREAM_MODE: Flag booleano (valore 1 o 0, default 0) per attivare la
    ricezione e la visualizzazione a schermo dei token in tempo reale (streaming
    SSE).
  - OUTPUT_MODE: Configura lo stile di visualizzazione dei risultati restituiti
    dallo script ("text", "raw", "json", "pretty").
  - THRESHOLD: Soglia limite espressa in caratteri al di sopra della quale i
    risultati delle API vengono salvati nello storico (default 1000).
  - MAX_RETRIES: Limite di tentativi di connessione da effettuare in caso di
    errori di rete temporanei (default 1).
  - SUPPORTED_PROVIDERS: Elenco testuale dei provider supportati (default "groq
    gemini huggingface").
  - CURL_BASE_OPTS: Array contenente i parametri base immutabili passati a curl
    per ogni chiamata di rete (--silent, --show-error, --no-buffer,
    --max-time 120).
  - FALLBACK_PAYLOAD: Payload Base64 alternativo impostato da un hook di
    post-esecuzione in caso di fallimento della chiamata API principale.

        Bearer token negli argomenti di processo (argv), rendendoli del tutto
        invisibili a strumenti di ispezione del sistema come ps, top o /proc.
      - Input: $1 (metodo HTTP, default "POST"), $2 (URL API), $3 (chiave API),
        $4 (file payload), $5 (file output), $6 (file log errori), $7 (flag
        streaming 1/0), $8 (riferimento ad array opzioni cURL extra).
      - Output: Restituisce lo stato HTTP o il codice di uscita di curl.
      - Side-effects: Connessione di rete, allocazione e cancellazione immediata
        di file temporanei per gli header su file descriptor, scrittura file di
        risposta e log.
      - Dipendenze: Funzione _tmpf, comandi printf, chmod, exec, curl, rm.

      - Output: Assegna il verdetto booleano a BASH4LLM_EDGE_EMPTY (1 se
        rilevato caso vuoto anomalo, 0 altrimenti) e memorizza i dettagli in
        variabili globali (BASH4LLM_EDGE_REQ_ID, BASH4LLM_EDGE_FINISH_REASON,
        BASH4LLM_EDGE_COMPLETION_TOKENS).
      - Side-effects: Duplicazione temporanea del file per l'analisi sicura.
      - Dipendenze: Funzioni _tmpf, is_valid_json_file, comandi cp, jq, rm.

  - finalize_and_output

      - Scopo: Formatta e visualizza i risultati finali generati in base alla
        modalità selezionata in $OUTPUT_MODE (text, raw, json o pretty).
        Inoltre, se l'output testuale supera la soglia di caratteri $THRESHOLD o
        se è forzato dall'utente, si occupa di salvare i risultati nel
        file-system (all'interno di $OUT_PATH o nella directory storica standard
        $BASH4LLM_HISTORY_DIR) sotto lock concorrenziale con umask blindata.
      - Input: $1 (formato: json, pretty, raw, text), $2 (stringa di testo del
        risultato).
      - Output: Output stampato a schermo secondo la formattazione richiesta.
        File archiviato fisicamente su disco se abilitato. Ritorna stato 0 o
        codice d'errore BASH4LLM_ERR_TMP.
      - Side-effects: Scrittura a schermo, salvataggio file storico
        transazionale, creazione directory via safe_mkdir.
      - Dipendenze: Funzioni _tmpf, safe_mkdir, lock_exec, log_error, log_warn,
        comandi cp, cat, jq, printf, wc, tr, date, dirname, chmod.

  - perform_request_once

      - Scopo: Orchestra l'esecuzione complessiva di una chiamata API sincrona
        sotto lock concorrenziale di thread, integrando l'esecuzione di hook
        isolati pre e post via execute_isolated_hook, la verifica del rate limit
        locale (check_local_rate_limit), ed un ciclo di retry automatico in caso
        di errori di rete temporanei (fino a $MAX_RETRIES tentativi). Gestisce
        l'estrazione dei testi, la diagnostica dei casi vuoti anomali
        (detect_empty_edge_case), la notifica degli errori formali inviati dalle
        API e la scrittura dello stato dell'ultima transazione in last_api.json.
        Formatta i risultati e restituisce lo stato d'uscita.
      - Input: Nessuno.
      - Output: Output generato stampato su console e file di log aggiornati.
        Ritorna stato 0 se completata, codice d'errore BASH4LLM_ERR_API se
        fallisce.
      - Side-effects: Invocazione di hook isolati, tentativi multipli di rete,
        sospensione temporanea del processo (sleep), aggiornamenti dello stato
        UI, messaggi diagnostici su stderr, gestione dei segnali e del file
        descriptor lock del thread.
      - Dipendenze: Funzioni acquire_thread_lock, release_thread_lock,
        execute_isolated_hook, check_local_rate_limit, call_api_once,
        extract_text_from_resp, detect_empty_edge_case, ui_state_write,
        extract_api_error, finalize_and_output, log_info, log_error, log_warn,
        b64decode, comandi trap, jq, head, sleep, printf.

  - collect_input_from_files

      - Scopo: Legge e concatena in un'unica stringa i contenuti di una lista di
        file di input passati via opzione -f, validandone preventivamente la
        sicurezza tramite validate_file_input ed inserendo delimitatori visivi
        strutturati tra i file.
      - Input: Array di percorsi di file ($@).
      - Output: Stringa di testo unificata stampata su stdout. Interrompe lo
        script con errore BASH4LLM_ERR_SEC (17) se un file contiene byte nulli o
        dati non sicuri, o BASH4LLM_ERR_TMP se non leggibile.
      - Side-effects: Lettura file-system.
      - Dipendenze: Funzioni file_readable, validate_file_input, log_error,
        comandi cat.

  - expand_args_to_content

      - Scopo: Converte gli argomenti CLI posizionali in frammenti di prompt. Se
        un argomento corrisponde a un percorso file esistente e leggibile, ne
        valida la sicurezza via validate_file_input e ne legge il contenuto,
        altrimenti lo accoda direttamente come testo letterale.
      - Input: Elementi accumulati nell'array $ARGS.
      - Output: Stringa di prompt unificata stampata su stdout.
      - Side-effects: Lettura file-system.
      - Dipendenze: Funzioni file_readable, validate_file_input, log_error,
        comandi cat.

  - file_readable

      - Scopo: Convalida se il percorso indicato corrisponde a un file regolare
        effettivamente leggibile dall'utente corrente.
      - Input: $1 (percorso file).
      - Output: Ritorna stato 0 se leggibile, 1 in caso contrario.
      - Side-effects: Nessuno.
      - Dipendenze: Test shell [ -r ... ] && [ -f ... ].

  - trim

      - Scopo: Rimuove gli spazi vuoti, i tabulatori e i caratteri di a capo
        dall'inizio e dalla fine di una stringa testuale passata tramite awk.
      - Input: $1 (stringa da pulire).
      - Output: Stringa pulita stampata su stdout.
      - Side-effects: Nessuno.
      - Dipendenze: Comandi awk, printf.

  - is_number

      - Scopo: Verifica se il valore testuale fornito rappresenta un valore
        numerico valido (intero o decimale).
      - Input: $1 (stringa da analizzare).
      - Output: Ritorna stato 0 se numerico, 1 altrimenti.
      - Side-effects: Nessuno.
      - Dipendenze: Comandi awk, printf.

  - is_supported_model

      - Scopo: Analizza il nome del modello e ne convalida la compatibilità con
        Bash4LLM⁺. Filtra e scarta (ritornando stato 1) modelli che richiedono
        formati non-testuali esclusivi (immagini, visione/VQA,
        audio/speech/whisper, tts, embedding o vettori, modelli multimodali
        non-standard), garantendo che siano inviati solo modelli di testo
        compatibili.
      - Input: $1 (nome del modello).
      - Output: Ritorna stato 0 se supportato, 1 se escluso.
      - Side-effects: Nessuno.
      - Dipendenze: Comando tr.

  - list_models_cli

      - Scopo: Formatta e visualizza sulla console l'elenco dei modelli
        disponibili memorizzati in locale normalizzandoli con
        _normalize_model_name, evidenziando chiaramente quali modelli non sono
        supportati (perché richiedono input non-testuali) in modo che l'utente
        non selezioni configurazioni non ammesse.
      - Input: Nessuno (scansiona $MODELS_FILE).
      - Output: Elenco stampato su stderr. Ritorna stato 0 se completato, 1 se
        il file dei modelli è assente o vuoto.
      - Side-effects: Scrittura su stderr.
      - Dipendenze: Funzioni _normalize_model_name, is_supported_model, comando
        printf.

  - validate_model_core

      - Scopo: Algoritmo centrale di validazione dei modelli. Normalizza il nome
        tramite _normalize_model_name. Controlla se è registrato nel file dei
        modelli locali e verifica se è escluso per via di formati non testuali
        via is_supported_model.
      - Input: $1 (nome modello).
      - Output: Ritorna stato 0 se valido, 1 in caso d'errore (emettendo
        dettagli su stderr).
      - Side-effects: Scrittura messaggi su stderr.
      - Dipendenze: Funzioni _normalize_model_name, is_supported_model, comandi
        grep, awk, printf.

  - load_local_config

      - Scopo: Carica in memoria i parametri di configurazione definiti
        dall'utente nel file di configurazione locale (config all'interno della
        cartella $BASH4LLM_CONFIG_DIR), interpretando le righe chiave/valore e
        impostando le variabili globali corrispondenti (MODEL, TEMPERATURE/TURE,
        MAX_TOKENS, OUTPUT_MODE/FORMAT, THRESHOLD). Ignora commenti e righe
        vuote e pulisce gli spazi vuoti nativamente.
      - Input: Nessuno.
      - Output: Assegnazione di variabili globali di ambiente.
      - Side-effects: Modifica delle variabili globali in memoria.
      - Dipendenze: Lettura file-system.

  - load_whitelist

      - Scopo: Carica in memoria e normalizza l'elenco di tutti i modelli
        autorizzati presenti nel file dei modelli locali tramite normalizzazione
        riga per riga di _normalize_model_name per comporre la stringa globale
        di whitelist $ALLOWED_MODELS usata per i filtri di convalida dei
        modelli.
      - Input: Nessuno (analizza $MODELS_FILE).
      - Output: Popola la variabile globale ALLOWED_MODELS con i nomi
        normalizzati separati da a capo.
      - Side-effects: Modifica della variabile globale ALLOWED_MODELS.
      - Dipendenze: Funzione _normalize_model_name.

  - is_tty_out

      - Scopo: Verifica se lo standard output (stdout) dello script è collegato
        a un terminale interattivo (TTY) reale anziché essere ridiretto a un
        file o pipeline.
      - Input: Nessuno.
      - Output: Ritorna stato 0 se TTY, 1 in caso contrario.
      - Side-effects: Nessuno.
      - Dipendenze: Test shell [ -t 1 ].

BLOCCHI DI CODICE

  - CORE_SETUP_INPUT_HELPERS

      - Fase: Assemblaggio dell'input, anonimizzazione e gestione del sourcing

      - Azione: Definisce le routine di lettura e validazione di file ed

  - CORE_SETUP_CLI_PARSE

      - Azione: Analizza in un ciclo iterativo tutti i parametri CLI. Supporta

        crittografico (--vault), l'orchestrazione della suite di test
        (--test/--run-all-tests), l'installazione estensioni (--install-extras),

  - CORE_SETUP_SESSION_ENGINE

      - Azione: Rileva e tenta di importare lo script del Session Engine esterno
        (session-engine.sh). Esegue la verifica di sicurezza del percorso e la
        convalida dell'integrità crittografica SHA-256 rispetto al manifesto. Se
        validato, esegue un test di sintassi (bash -n) e ne carica le funzioni
        abilitando _engine_available=1 per la gestione avanzata e la

        il fallback sui metodi storici legacy.

  - CORE_SETUP_NORM_FLAGS

      - Fase: Normalizzazione dei flag e censimento dinamico dei plug-in.
      - Azione: Imposta i valori di default di ALLOW_API_CALLS, esegue una

  - CORE_SETUP_ACTIONS

      - Fase: Esecuzione delle azioni amministrative ed offline immediate.
      - Azione: Elabora ed esegue immediatamente i comandi che non richiedono

        ridenominazione dei metadati di un thread (--rename-thread), listati dei
        provider e dei modelli, impostazione del modello predefinito
        (--set-default), delega transazionale all'orchestratore della test suite
        master (--test), installazione delle estensioni (--install-extras) con

        sui permessi (700/600) e verifica dei digest SHA-256 contro il file
        manifesto manifest.sha256, ed infine l'inizializzazione transazionale di
        un nuovo thread (--init-thread). Esce con stato 0 al termine
        dell'operazione richiesta.

5. CORE_PROVIDER

VARIABILI

  - _supported_providers_arr: Array interno utilizzato per la memorizzazione e
    l'indicizzazione dinamica di tutti i moduli provider rilevati ed installati
    nella directory delle estensioni.
  - SUPPORTED_PROVIDERS: Elenco testuale unificato dei provider supportati
    separati da caratteri di spazio.
  - PROVIDER: Identificatore del provider attivo (sincronizzato con la selezione
    persistita nel file canonico del provider o sovrascritta tramite CLI/menu
    interattivo).
  - PROVIDER_INTERACTIVE_SELECTED: Flag booleano interno (valore 1 o 0) che
    attesta l'avvenuta selezione del provider tramite menu interattivo da
    terminale.
  - FINAL_MODEL: Nome del modello finale validato e risolto dalla routine
    resolve_model, pronto per l'invio nelle chiamate API.
  - STDIN_CONTENT: Buffer di memoria adibito alla memorizzazione del flusso di
    testo catturato dallo standard input (cat -) in caso di redirezioni o
    pipeline.

FUNZIONI

  - validate_provider_interface

      - Scopo: Convalida che il modulo del provider attivo implementi
        correttamente le specifiche dell'interfaccia di Bash4LLM⁺. Verifica la
        presenza fisica in memoria delle funzioni obbligatorie
        (buildpayload_<provider> e call_api_<provider>), e traccia a scopo
        informativo la presenza o assenza dei metodi opzionali
        (call_api_streaming_<provider>, refresh_models_<provider>,
        validate_model_<provider>, auto_select_model_<provider>).
      - Input: $1 (nome identificativo del provider da analizzare).
      - Output: Ritorna stato 0 se l'interfaccia obbligatoria è pienamente
        implementata, 1 in caso contrario (emettendo errori critici loggati via
        log_error).
      - Side-effects: Scrittura di log di errore o informativi su stderr.
      - Dipendenze: Comandi type, funzioni log_error, log_info.

  - assemble_content

      - Scopo: Compila ed organizza la stringa del prompt di input principale
        $CONTENT che verrà inviata al modello LLM. Segue una catena di regole di
        priorità esclusive:
        1.  Se è configurato un JSON utente in $JSON_INPUT, pulisce la variabile
            $CONTENT ed esce (in quanto il JSON di input definisce autonomamente
            i messaggi).
        2.  Se l'utente ha inserito dei file via parametro -f ($FILE_INPUTS), ne
            raccoglie ed unifica i contenuti via collect_input_from_files
            (previa validazione di sicurezza validate_file_input). Se sono
            presenti argomenti posizionali aggiuntivi, li annette in coda come
            frammenti testuali.
        3.  Se è richiesto l'uso di un template ($TEMPLATE), preleva il file del
            modello dalla directory dei template, esegue la sostituzione della
            stringa segnaposto {{CONTENT}} rimpiazzandola con il prompt inserito
            (proveniente da file, da stdin o da argomenti posizionali) usando
            awk con file di staging intermedi temporanei, e assegna il testo
            risultante a $CONTENT.
        4.  Se è presente dell'input catturato dallo standard input
            ($STDIN_CONTENT), lo adotta come prompt principale, allegando in
            coda eventuali argomenti posizionali.
        5.  Se vi sono solo argomenti CLI posizionali in $ARGS, li converte ed
            unisce nel prompt testuale principale via expand_args_to_content.
      - Input: Variabili globali JSON_INPUT, FILE_INPUTS, TEMPLATE,
        STDIN_CONTENT, ARGS, BASH4LLM_TEMPLATES_DIR, RUN_TMPDIR.
      - Output: Stringa compilata assegnata alla variabile globale CONTENT.
        Ritorna stato 0.
      - Side-effects: Lettura file, generazione e distruzione di file di staging
        temporanei atomici sul disco tramite _mktemp_in_dir, sostituzione di
        stringhe via awk.
      - Dipendenze: Funzioni collect_input_from_files, expand_args_to_content,
        ensure_run_tmpdir, _mktemp_in_dir, comandi cat, awk, mv, rm, printf.

BLOCCHI DI CODICE

  - CORE_PROVIDER_PRO_LOAD_INITIALIZATION

      - Fase: Selezione, persistenza e caricamento del modulo provider attivo.
      - Azione: Scansiona la directory dei provider esterni per mappare i moduli
        installati. Determina il provider attivo leggendolo dai parametri CLI o
        dal file di configurazione canonico del provider $PROVIDER_FILE
        (adottando "groq" in caso di assenza).
          - Se specificato un nuovo provider da CLI ($PROVIDER_CLI diverso da
            "list" e non interattivo): convalida l'appartenenza ai provider
            supportati, salva transazionalmente la scelta nel file
            $PROVIDER_FILE con permessi 600 via atomic_write, rimuove il vecchio
            file URL del provider e risolve il nuovo endpoint.
          - Se richiesta la selezione interattiva (--provider senza argomenti o
            valore "list"): visualizza a schermo il menu numerato dei provider
            disponibili evidenziando il predefinito corrente, acquisisce la
            scelta dell'utente da stdin (accettando l'indice o il nome letterale
            e adottando il default se premuto invio), scrive in modo atomico la
            scelta in $PROVIDER_FILE con permessi 600 via atomic_write, rimuove
            il vecchio file URL del provider e risolve il nuovo URL.
          - Se il provider attivo è "groq" e manca il file URL locale, scrive
            l'URL dell'API predefinito nel file canonico tramite
            write_provider_url_if_missing. Invoca la funzione di caricamento
            sicuro load_provider_module per importare le funzioni del modulo
            provider ed esegue la risoluzione dell'URL dell'API. Se
            l'interfaccia interattiva viene eseguita senza comandi aggiuntivi,
            stampa la conferma del provider impostato ed esce direttamente con
            stato 0.

  - CORE_PROVIDER_PRO_LOAD_VALIDATION_REFRESH

      - Fase: Validazione del modulo provider ed allineamento modelli.
      - Azione: Verifica che il modulo del provider sia stato correttamente
        importato ed esegue la convalida della conformità della sua interfaccia
        via validate_provider_interface; in caso di errori strutturali termina
        con codice BASH4LLM_ERR_API. Se è stato richiesto esplicitamente il
        refresh dei modelli ($REFRESH_MODELS attivo), assicura la presenza della
        chiave API via ensure_api_key_for_provider ed avvia l'allineamento dei
        modelli locali tramite refresh_models_dispatch, terminando con stato 0.
        In subordine, se il file dei modelli locali $MODELS_FILE è assente o
        completamente vuoto, tenta di eseguire un allineamento automatico dei
        modelli in background (richiedendo la chiave API ed invocando la routine
        di refresh, senza interrompere lo script in caso di fallimento per
        permettere l'elaborazione dei flussi).

  - CORE_PROVIDER_SHOW

      - Fase: Esecuzione delle risposte diagnostiche immediate.
      - Azione: Gestisce e satisfies le richieste diagnostiche e di ispezione
        dei percorsi dello script, terminando l'esecuzione con stato 0 dopo la
        visualizzazione dei dati:
          - --print-config-dir / PRINT_CONFIG_DIR: Stampa il percorso della
            directory di configurazione canonica.
          - --print-provider-file / PRINT_PROVIDER_FILE: Stampa il percorso del
            file canonico del provider.
          - PRINT_MODEL_FILE: Stampa il percorso del file del modello canonico
            per il provider indicato.
          - SHOW_CONFIG: Visualizza un riepilogo tabulare dettagliato dei
            parametri correnti dell'installazione (versione, date, provider
            attivo, modello attivo, temperatura, token massimi, formato output,
            soglia di salvataggio).
          - DIAGNOSTICS: Esegue un'analisi di integrità diagnostica completa
            dello stato del sistema: scansiona e verifica l'esistenza e
            l'accessibilità fisica di tutte le directory operative, verifica lo
            stato del file di manifesto dell'integrità delle estensioni,
            controlla lo stato di abilitazione del Key Vault OpenSSL, lo stato
            di sblocco della sessione (_B4L_RT_CTX), il supporto PBKDF2, lo
            stato di inizializzazione del Vault ed esegue un test reale di TLS
            Handshake verso l'endpoint remoto attivo del provider via
            diagnose_tls_connection.

  - CORE_PROVIDER_MAIN_RESOLVE

      - Fase: Risoluzione del modello e cattura dello standard input.
      - Azione: Se l'avvio è per solo bootstrap ($BOOTSTRAP_ONLY attivo), esce
        immediatamente con stato 0. Carica le configurazioni locali via
        load_local_config e le whitelist dei modelli via load_whitelist,
        garantisce la stabilità della directory temporanea $RUN_TMPDIR, risolve
        il modello LLM finale da adottare via resolve_model ed esegue su di esso
        le convalide sintattiche e di interfaccia del provider
        (validate_model_core e validate_model_dispatch), terminando con codice
        BASH4LLM_ERR_BAD_MODEL se falliscono. Infine, cattura l'eventuale flusso
        di testo in arrivo da una redirezione o pipeline nello standard input
        (cat -) all'interno di STDIN_CONTENT e, in presenza di un JSON
        strutturato, ne estrae transazionalmente la chiave API interna ed i
        prompt d'ingresso sovrascrivendo e cancellando immediatamente il buffer
        per sicurezza.

  - CORE_PROVIDER_MAIN_EXECUTION

      - Fase: Esecuzione principale del prompt (Core Execution Loop).
      - Azione: Invoca assemble_content per generare il prompt definitivo. Se lo
        script è stato richiamato in modalità interattiva e non contiene prompt,
        visualizza la notifica del provider attivo ed esce. Esegue controlli di
        sicurezza sull'input bloccando l'esecuzione con codice
        BASH4LLM_ERR_NO_PROMPT in assenza di prompt testuale o JSON d'input
        (tranne se in chat interattiva, inizializzazione thread o elaborazione
        batch). Procede quindi con i tre flussi di esecuzione principali:
        1.  Elaborazione BATCH ($BATCH_FILE attivo): Scansiona il file batch
            riga per riga, escludendo righe vuote o commenti. Per ciascun prompt
            configura l'ambiente di thread se richiesto (validando l'ID thread,
            limitando la finestra dei messaggi, e richiamando
            session_engine_build_window o la legacy thread_read_window per
            compilare il JSON storico $BUILD_MESSAGES_FILE). Dispaccia la
            costruzione del payload via build_payload_from_vars, assicura la
            chiave API via ensure_api_key_for_provider ed avvia l'interrogazione
            dell'API (sincrona via perform_request_once o in streaming via
            call_api_streaming).
        2.  Chat Interattiva ($CHAT_MODE attivo): Trasferisce atomicamente
            l'esecuzione sostituendo l'immagine di processo dello script (exec
            bash) con l'utility esterna TUI REPL (tui-repl.sh) previa verifica
            di sicurezza del percorso e convalida dell'integrità crittografica
            SHA-256 via verify_module_integrity.
        3.  Esecuzione Singolo Prompt (Streaming o Sincrona):
              - Se è definito un thread operativo ($THREAD_ID), esegue la
                validazione dell'ID, determina la finestra di recupero, e
                compila il file storico dei messaggi $BUILD_MESSAGES_FILE
                interrogando il Session Engine o richiamando la routine legacy
                di lettura NDJSON.
              - Compila il payload JSON via build_payload_from_vars.
              - Se si opera in esecuzione reale (non simulata DRY_RUN), valida e
                recupera la chiave API del provider via
                ensure_api_key_for_provider.
              - Se Streaming attivo ($STREAM_MODE == 1): Invoca la funzione di
                streaming dedicada (call_api_streaming) sotto lock esclusivo di
                thread. Se completato con successo, e non in modalità simulata
                DRY_RUN, sanifica ed accoda il messaggio dell'utente ed il testo
                restituito dall'assistente nel registro NDJSON del thread
                (delegando al Session Engine o alla legacy thread_append).
