SPECIFICA DELL'ARCHITETTURA E DELLA LOGICA DI BASH4LLM⁺ (v2.8.5)

Questo documento descrive in modo completo e senza perdita di informazioni la
logica, le variabili, le funzioni e i blocchi strutturali del sistema Bash4LLM⁺,
suddivisi secondo le cinque macro-sezioni reali.

1.  PRECORE_BOOT

VARIABILI

  - SCRIPT_NAME: Nome identificativo del programma (impostato a "bash4llm").
  - SCRIPT_VERSION: Versione corrente del software (impostata a "2.8.5").
  - SCRIPT_DATE: Data di rilascio dello script (impostata a "2026-08-07").
  - BASH4LLM_SUPPORTED_PROVIDER_API: Versione del contratto d'interfaccia API
    supportata dal core per i moduli provider (valore numerico 1).
  - BASH4LLM_PLAT_ANDROID: Flag booleano (valore 1 o 0) impostato su bootstrap
    indicante se il runtime è eseguito sotto ambiente Termux/Android.
  - BASH4LLM_PLAT_MACOS: Flag booleano (valore 1 o 0) impostato su bootstrap
    indicante se il runtime è eseguito sotto sistema macOS/Darwin.
  - BASH4LLM_PLAT_WSL: Flag booleano (valore 1 o 0) impostato su bootstrap
    indicante se il runtime è eseguito sotto Windows Subsystem for Linux (WSL).
  - BASH4LLM_PLAT_CYGWIN: Flag booleano (valore 1 o 0) impostato su bootstrap
    indicante se l'esecuzione avviene sotto ambienti Windows compatibili Cygwin,
    MSYS2 o MinGW.
  - BASH4LLM_PLAT_BSD: Flag booleano (valore 1 o 0) impostato su bootstrap
    indicante se l'esecuzione avviene sotto sistemi FreeBSD, OpenBSD, NetBSD o
    DragonFly.
  - BASH4LLM_PLAT_LINUX: Flag booleano (valore 1 o 0) impostato su bootstrap
    indicante se l'esecuzione avviene sotto ambiente Linux generico o WSL.
  - BASH4LLM_KEY_MANUAL_PROMPT: Flag di stato interno (valore 1 o 0) per
    tracciare se una chiave API è stata inserita manualmente dall'utente via
    prompt TTY, con reset iniziale a 0 per prevenire leakage di variabili
    d'ambiente.
  - VALIDATE_SML: Flag di controllo (valore 1 o 0, default 0) per l'attivazione
    della validazione sintattica dello standard SML v2.0 sulle risposte LLM.
  - VALIDATE_REGEX: Stringa contenente l'espressione regolare POSIX ERE per la
    validazione della risposta estratta (default vuoto).
  - SANITIZE_OUTPUT: Flag di controllo (valore 1 o 0, default 0) per l'attivazione
    della sanificazione ANSI e caratteri speciali sul testo finale.
  - JSON_DIAGNOSTICS: Flag di controllo (valore 1 o 0, default 0) per l'emissione
    della diagnostica di errore in formato JSON strutturato su stderr.
  - BASH4LLM_MODEL_CACHE: Array associativo adibito ad archiviare in memoria i
    nomi dei modelli normalizzati per evitare ricalcoli regex costosi in tempo
    di esecuzione.
  - C_LOGO, C_BANNER, C_RST, C_BOLD, C_NOBOLD, C_UNDERLINE, C_NOUNDERLINE,
    C_BLACK, C_RED, C_GREEN, C_YELLOW, C_BLUE, C_MAGENTA, C_CYAN, C_WHITE,
    C_BBLACK, C_BRED, C_BGREEN, C_BYELLOW, C_BBLUE, C_BMAGENTA, C_BCYAN,
    C_BWHITE, BG_BLACK, BG_RED, BG_GREEN, BG_YELLOW, BG_BLUE, BG_MAGENTA,
    BG_CYAN, BG_WHITE: Sequenze di escape ANSI per la formattazione di testo,
    colori e sfondi nel terminale, disattivate in presenza dello standard
    NO_COLOR o TERM=dumb.
  - BASH4LLM_ERR_NO_API_KEY: Costante numerica di errore (valore 10) associata
    alla mancanza di una chiave API.
  - BASH4LLM_ERR_BAD_MODEL: Costante numerica di errore (valore 11) associata
    alla richiesta di un modello non valido o non supportato.
  - BASH4LLM_ERR_CURL_FAILED: Costante numerica di errore (valore 12) associata
    al fallimento della chiamata di rete curl.
  - BASH4LLM_ERR_PARSE: Costante numerica di errore (valore 13) associata a
    fallimenti di parsing JSON o errori sintattici.
  - BASH4LLM_ERR_NO_PROMPT: Costante numerica di errore (valore 14) associata
    alla mancanza di un prompt di input.
  - BASH4LLM_ERR_TMP: Costante numerica di errore (valore 15) associata a
    problemi del file-system temporaneo o dei file di lock.
  - BASH4LLM_ERR_API: Costante numerica di errore (valore 16) associata a
    risposte d'errore o codici HTTP non validi restituiti dal provider API.
  - BASH4LLM_ERR_SEC: Costante numerica di errore (valore 17) associata a
    vulnerabilità sul file-system, permessi non sicuri o violazioni della policy
    di sicurezza e integrità SHA-256.
  - BASH4LLMERR_NO_API_KEY: Mappatura alias diretta del valore di
    BASH4LLM_ERR_NO_API_KEY con notazione ad underscore.
  - BASH4LLMERR_BAD_MODEL: Mappatura alias diretta del valore di
    BASH4LLM_ERR_BAD_MODEL con notazione ad underscore.
  - BASH4LLMERR_CURL_FAILED: Mappatura alias diretta del valore di
    BASH4LLM_ERR_CURL_FAILED con notazione ad underscore.
  - BASH4LLMERR_PARSE: Mappatura alias diretta del valore di BASH4LLM_ERR_PARSE
    con notazione ad underscore.
  - BASH4LLMERR_NO_PROMPT: Mappatura alias diretta del valore di
    BASH4LLM_ERR_NO_PROMPT con notazione ad underscore.
  - BASH4LLMERR_TMP: Mappatura alias diretta del valore di BASH4LLM_ERR_TMP con
    notazione ad underscore.
  - BASH4LLMERR_API: Mappatura alias diretta del valore di BASH4LLM_ERR_API con
    notazione ad underscore.
  - BASH4LLMERR_SEC: Mappatura alias diretta del valore di BASH4LLM_ERR_SEC con
    notazione ad underscore.
  - DEBUG: Flag di configurazione per l'output di tracciamento dello sviluppo.
    Eredita il valore di ambiente ${DEBUG} o ${BASH4LLM_DEBUG}, o viene
    impostato su 0 (disattivo).
  - BASH4LLM_LOG: Percorso assoluto o relativo del file in cui registrare i log
    di tracciamento. Eredita ${BASH4LLM_LOG} (vuoto se disattivato).
  - SCRIPTDIR: Percorso assoluto della directory contenente lo script corrente,
    risolto dinamicamente tramite la funzione resolve_script_dir.
  - BASH4LLM_DIR: Directory principale di installazione dei dati e delle
    configurazioni di Bash4LLM⁺. Dichiarata dall'ambiente o derivata da
    SCRIPTDIR/bash4llm.d.
  - BASH4LLM_CONFIG_DIR: Directory dei file di configurazione utente
    persistenti. Impostata a BASH4LLM_CONFIG_DIR di ambiente o posizionata sotto
    $BASH4LLM_DIR/config.
  - BASH4LLM_MODELS_DIR: Directory dei file relativi ai modelli supportati.
    Impostata a BASH4LLM_MODELS_DIR di ambiente o posizionata sotto
    $BASH4LLM_DIR/models.
  - BASH4LLM_TEMPLATES_DIR: Directory contenente i file dei modelli di template.
    Impostata a BASH4LLM_TEMPLATES_DIR di ambiente o posizionata sotto
    $BASH4LLM_DIR/templates.
  - BASH4LLM_HISTORY_DIR: Directory contenente lo storico e i log delle
    interazioni dello script. Impostata a BASH4LLM_HISTORY_DIR di ambiente o
    posizionata sotto $BASH4LLM_DIR/history.
  - BASH4LLM_TMPDIR: Directory radice per l'allocazione dei dati temporanei di
    Bash4LLM⁺. Impostata a BASH4LLM_TMPDIR di ambiente o posizionata sotto
    $BASH4LLM_DIR/tmp.
  - BASH4LLM_RUN_DIR: Directory isolata per i file di stato ed esecuzione del
    runtime. Impostata sotto $BASH4LLM_DIR/var/run.
  - BASH4LLM_LOCKS_DIR: Directory dedicata alla memorizzazione isolata dei file
    di lock concorrenziali. Impostata sotto $BASH4LLM_RUN_DIR/locks.
  - CANONICAL_EXTRAS_DIR: Percorso della directory canonica delle estensioni vendor,
    calcolato rimuovendo la barra finale da BASH4LLM_DIR e annettendo /extras.
  - LEGACY_EXTRAS_DIR: Percorso storico di fallback delle estensioni, relativo
    alla cartella dello script (SCRIPTDIR/extras).
  - BASH4LLM_EXTRAS_DIR: Directory attiva per l'accesso alle risorse aggiuntive
    vendor (assegnata a CANONICAL_EXTRAS_DIR).
  - PROVIDERS_DIR: Percorso assoluto o relativo dei moduli vendor dei provider
    (impostato su PROVIDERS_DIR di ambiente o localizzato sotto $BASH4LLM_EXTRAS_DIR/providers).
  - CANONICAL_LOCAL_EXTRAS_DIR: Percorso della directory canonica delle estensioni
    utente locali ($BASH4LLM_DIR/local-extras).
  - BASH4LLM_LOCAL_EXTRAS_DIR: Directory radice per le estensioni utente locali.
  - LOCAL_PROVIDERS_DIR: Directory contenente i provider definiti localmente
    dall'utente ($BASH4LLM_LOCAL_EXTRAS_DIR/providers).
  - THREAD_DIR: Directory dedicata alla registrazione dei log storici NDJSON dei
    thread operativi (posizionata in $BASH4LLM_HISTORY_DIR/threads).
  - TMPDIR: Override dell'ambiente di sistema forzato su BASH4LLM_TMPDIR per
    garantire l'isolamento locale e sicuro di cURL e dei file provvisori.
  - BASH4LLM_RATES_DIR: Directory isolata per la memorizzazione dei marcatori
    transazionali del rate limiting locale (posizionata in
    $BASH4LLM_TMPDIR/rates).
  - BASH4LLM_VAULT_ENABLED: Variabile di controllo per l'abilitazione (1) o
    disattivazione (0) del Key Vault OpenSSL. Prelevata dal file config o
    impostata di default a 1.
  - _BASH4LLM_OPENSSL_HELPER: Percorso dello script di supporto OpenSSL Vault
    ($BASH4LLM_EXTRAS_DIR/security/openssl-helper.sh).
  - BASH4LLM_OPENSSL_ACTIVE: Flag booleano interno indicante se
    openssl-helper.sh è stato validato tramite SHA-256 e caricato nel runtime.
  - MODELS_FILE: File di testo locale in cui memorizzare la lista dei modelli
    recuperati per il provider attivo, sincronizzato tramite
    sync_models_file_path.
  - MAX_MODELS: Limite numerico massimo di modelli importabili o gestibili
    localmente. Eredita ${MAX_MODELS} o adotta il valore di default di 200.
  - PROVIDER_FILE: Percorso del file che persists l'ultimo provider configurato
    dall'utente, determinato tramite canonical_provider_file.
  - MODELS_LOCK: Percorso del file di lock di sincronizzazione per l'accesso ai
    modelli, posizionato sotto $BASH4LLM_LOCKS_DIR/models.lock.
  - HISTORY_LOCK: Percorso del file di lock per l'accesso concorrente ai log di
    storico e sessione, posizionato sotto $BASH4LLM_HISTORY_DIR/history.lock.
  - TMP_LOCK: Percorso del file di lock esclusivo per la gestione sicura della
    directory temporanea dello script, posizionato sotto
    $BASH4LLM_LOCKS_DIR/tmp.lock.
  - BASH4LLM_LOCK_TIMEOUT_TMP: Timeout massimo di attesa espresso in secondi per
    acquisire il lock temporaneo (eredita BASH4LLM_LOCK_TIMEOUT_TMP o
    imposta 10).
  - BASH4LLM_LOCK_TIMEOUT_MODELS: Timeout in secondi per acquisire il lock sui
    modelli (eredita BASH4LLM_LOCK_TIMEOUT_MODELS o imposta 10).
  - BASH4LLM_LOCK_TIMEOUT_HISTORY: Timeout in secondi per acquisire il lock
    sullo storico dei messaggi e dei thread (eredita
    BASH4LLM_LOCK_TIMEOUT_HISTORY o imposta 10).

FUNZIONI

  - resolve_script_dir: Identifica la cartella reale in cui risiede lo script in
    esecuzione, risolvendo i collegamenti simbolici sul file-system. Input:
    Nessuno (analizza la variabile speciale ${BASH_SOURCE[0]}). Output:
    Restituisce su stdout il percorso assoluto normalizzato della directory.
    Dipendenze: readlink, dirname, cd, pwd, printf.
  - safe_mkdir: Crea in sicurezza una directory con i permessi specificati,
    verificando che non coincida con un collegamento simbolico (mitigazione
    symlink attack). Input: $1 (directory), $2 (opzionale: permessi ottali,
    default 700). Output: Stato 0 o arresto immediato con codice d'uscita 15
    (BASH4LLM_ERR_TMP) se fallisce. Dipendenze: mkdir, chmod, printf.
  - check_required_arg: Convalida la presenza del parametro CLI obbligatorio
    richiesto da un'opzione, verificando la prossimità del limite posizionale
    degli argomenti. Input: $1 (opzione indagata), $2 (conteggio argomenti
    residui). Output: Stato 0 o arresto con codice 15. Dipendenze: log_error.
  - canonical_config_dir: Normalizza il percorso della directory di
    configurazione rimuovendo slash finali. Input: Nessuno
    ($BASH4LLM_CONFIG_DIR). Output: Restituisce il percorso su stdout.
    Dipendenze: printf.
  - canonical_provider_file: Genera il percorso canonico del file di persistenza
    del provider. Input: Nessuno. Output: Percorso del file /provider su stdout.
    Dipendenze: printf, canonical_config_dir.
  - canonical_model_file: Genera il percorso del file in cui memorizzare il
    modello di default per il provider attivo. Input: $1 (provider). Output:
    Percorso del file /model. su stdout. Dipendenze: printf,
    canonical_config_dir.
  - canonical_provider_url_file: Genera il percorso del file contenente l'URL
    API del provider attivo. Input: Nessuno. Output: Percorso del file
    /provider-url su stdout. Dipendenze: canonical_config_dir, printf.
  - trim_space: Rimuove spazi e tabulazioni iniziali e finali tramite costrutti
    di scomposizione nativi della shell (senza fork). Input: $1 (stringa).
    Output: Stringa pulita su stdout. Dipendenze: printf.
  - _is_readonly_func: Verifica se una funzione esiste ed è dichiarata come
    read-only in memoria tentandone l'unset in una sotto-shell. Input: $1
    (nome funzione). Output: Stato 0 (read-only) o 1. Dipendenze: declare, unset.
  - sync_models_file_path: Sincronizza il percorso globale di MODELS_FILE
    basandosi sul provider attivo, forzando una sanitizzazione protettiva contro
    directory traversal che esclude caratteri non alfanumerici (eccetto trattino
    e trattino basso). Input: $1 (opzionale: provider). Output: Esporta la
    variabile MODELS_FILE in ambiente. Dipendenze: export.
  - normalize_model_name: Esegue la normalizzazione dei nomi dei modelli
    rimuovendo spazi, ritorni a capo ed i prefissi models/ e . Per ottimizzare
    il runtime, conserva i risultati in un array associativo di cache in
    memoria. Input: $1 (nome modello). Output: Nome normalizzato su stdout.
    Dipendenze: normalize_model.
  - is_truthy: Valuta se la stringa rappresenta un valore booleano vero (1,
    true, TRUE, True, yes, YES, Yes). Input: $1 (stringa). Output: Stato 0
    (vero) o 1 (falso).
  - _extract_notes_section: Estrae sezioni testuali letterali (senza esecuzione
    di codice) dal file di documentazione core-notes.sh. Input: $1 (titolo
    sezione target). Output: Righe estratte su stdout o stato 1 se assente.
    Dipendenze: awk.
  - emit_json_diagnostics: Genera ed emette messaggi di errore ed avviso in
    formato JSON strutturato su stderr quando JSON_DIAGNOSTICS è attivo.
    Input: $1 (status type, default "ERROR"), $2 (codice errore numerico), $3
    (reason code), $4 (messaggio). Output: Stringa JSON su stderr. Dipendenze:
    jq, date, printf.
  - log_prefix: Restituisce il prefisso di log "bash4llm: ". Input: Nessuno.
    Output: Prefisso su stdout. Dipendenze: printf.
  - log_info: Registra messaggi informativi. Se $DEBUG=1 scrive su stderr; se
    $BASH4LLM_LOG è definito, appende il record con timestamp UTC. Input: $1
    (categoria, default INFO), $2 (messaggio). Dipendenze: log_prefix, date,
    printf.
  - log_warn: Registra messaggi di avviso non critici su stderr e file
    $BASH4LLM_LOG. Input: $1 (modulo), $2 (messaggio). Dipendenze: log_prefix,
    date, printf.
  - log_error: Registra errori bloccanti su stderr e file $BASH4LLM_LOG. Se
    JSON_DIAGNOSTICS=1, delega l'emissione a emit_json_diagnostics. Input: $1
    (modulo), $2 (messaggio). Dipendenze: log_prefix, emit_json_diagnostics,
    is_truthy, date, printf.
  - log_info_user: Registra messaggi informativi di esecuzione destinati
    all'utente (non silenziati da QUIET) su stderr e file log. Input: $1
    (modulo), $2 (messaggio). Dipendenze: log_prefix, date, printf.
  - dbg: Stampa diagnostica su stderr se $DEBUG=1. Input: $* (argomenti).
    Dipendenze: printf.
  - read_secure_input: Acquisisce in modo sicuro input sensibili (chiavi API,
    password) disabilitando l'echo su /dev/tty prima di mostrare il prompt.
    Gestisce interruzioni via trap, pipe da stdin e valida la lunghezza minima.
    Input: $1 (var target), $2 (prompt), $3 (min len), $4 (allow verify).
    Output: Assegna input a var target via printf -v, stato 0 o 1. Dipendenze:
    stty, trap, printf, read.
  - validate_file_input: Esegue la convalida di sicurezza di un file di input,
    verificando esistenza, leggibilità, dimensione non nulla e assenza di byte
    nulli o controlli C0 incompatibili. Input: $1 (percorso file). Output:
    Codici stato: 0 (valido), 1 (vuoto), 2 (non leggibile), 3 (0 byte), 4
    (violazioni binarie). Dipendenze: tr, wc, file_size.
  - _get_perm_string: Restituisce stringa permessi simbolici portabile (Linux vs
    macOS/BSD) tramite platform checks. Input: $1 (percorso). Dipendenze: stat.
  - _get_owner: Identifica utente proprietario del file in modo portabile (Linux
    vs macOS/BSD) tramite platform checks. Input: $1 (percorso). Dipendenze:
    stat.
  - validate_path_security: Valida la sicurezza di un percorso verificando che
    il file e la directory genitrice non siano symlink, appartengano all'utente
    corrente e non siano group/world writable. Input: $1 (percorso). Output:
    Stato 0 (sicuro) o 1 (violazione). Dipendenze: _get_owner, _get_perm_string,
    log_error, log_warn, is_truthy, dirname, id, awk.
  - _core_sha256: Calcola l'hash crittografico SHA-256 digest di un file tramite
    i binari di sistema nativi (sha256sum, openssl, shasum). Input: $1 (file).
    Output: Hash esadecimale su stdout o stato 1. Dipendenze: sha256sum,
    openssl, shasum, awk.
  - verify_module_integrity: Verifica la sicurezza del percorso e l'integrità
    crittografica SHA-256 di un modulo rispetto al file extras/manifest.sha256.
    Input: $1 (percorso modulo), $2 (opzionale: dominio "vendor" o "local"), $3
    (opzionale: percorso relativo). Output: Stato 0 o BASH4LLM_ERR_SEC (17).
    Dipendenze: validate_path_security, _core_sha256, log_error, log_info, awk.
  - _provider_env_snapshot: Cattura uno snapshot in memoria delle variabili
    d'ambiente guscio (PATH, IFS, PWD, CDPATH, LANG, LC_ALL) prima dell'importazione
    di moduli provider. Input: Nessuno. Output: Popola variabili _B4L_SAVED_*.
  - _provider_env_restore: Ripristina le variabili d'ambiente guscio salvate da
    _provider_env_snapshot. Input: Nessuno. Output: Ripristina ambiente guscio.
    Dipendenze: export, unset, cd.
  - _verify_manifest_signature: Verifica la firma crittografica Ed25519 del file
    manifesto (manifest.sha256.sig) avvalendosi di OpenSSL o ssh-keygen e della
    chiave pubblica ufficiale official-ed25519.pub. Input: $1 (file manifesto).
    Output: Stato 0 o BASH4LLM_ERR_SEC (17). Dipendenze: validate_path_security,
    _tmpf, log_error, is_truthy, openssl, ssh-keygen, rm.
  - ensure_api_key_for_provider: Valida e acquisisce la chiave API per il
    provider selezionato seguendo la gerarchia: 1) OpenSSL Key Vault in memoria;
    2) Variabile d'ambiente (se BASH4LLM_REQUIRE_VAULT=0); 3) Prompt interattivo
    TTY via read_secure_input. Input: $1 (provider). Output: Stato 0 o
    BASH4LLM_ERR_NO_API_KEY (10) / BASH4LLM_ERR_SEC (17). Esporta la chiave API.
    Dipendenze: provider_api_env_var_name, vault_exists, vault_load_keys, jq,
    log_info_user, log_warn, log_error, read_secure_input, is_truthy, export.
  - enforce_network_policy: Determina se le chiamate di rete sono abilitate
    analizzando $DRY_RUN, $BASH4LLM_SKIP_NETWORK,
    $BASH4LLM_ENFORCE_NO_NETWORK_IF_QUIET e $QUIET. Input: Nessuno. Output:
    Stato 1 (bloccate) o 0 (autorizzate). Dipendenze: is_truthy, log_info.
  - ensure_config_dir: Assicura la presenza e l'accessibilità fisica della
    cartella config via safe_mkdir (chmod 700) e valida la scrivibilità tramite
    file di test temporaneo. Input: Nessuno. Output: Stato 0 o 1. Dipendenze:
    safe_mkdir, chmod, rm, log_error.
  - write_provider_url_if_missing: Registra l'URL API del provider in modo
    transazionale tramite file temporaneo di staging, applicandovi permessi 600.
    Input: $1 (provider), $2 (URL). Output: Stato 0 o 1. Dipendenze:
    canonical_provider_url_file, dirname, safe_mkdir, _tmpf, mv, cp, rm, chmod.
  - resolve_provider_url: Identifica ed esporta l'URL API per il provider
    selezionato. Controlla BASH4LLM_API_URL o BASH4LLM_PROVIDER_URL, il file
    /provider-url o l'endpoint predefinito Groq. Input: $1 (provider). Output:
    Stato 0 o 1. Esporta BASH4LLM_PROVIDER_URL. Dipendenze:
    canonical_provider_url_file, sed, awk, export.
  - provider_api_env_var_name: Calcola il nome standardizzato della variabile
    d'ambiente deputata a contenere la chiave API del provider (es: "groq" ->
    "GROQ_API_KEY"). Input: $1 (provider). Output: Nome normalizzato su stdout.
    Dipendenze: printf.
  - print_persistence_reminder: Stampa avviso su stderr con istruzioni per
    rendere persistente una chiave API inserita manualmente durante la sessione.
    Input: Nessuno (BASH4LLM_KEY_MANUAL_PROMPT). Output: Stampa avviso e azzera
    flag. Dipendenze: provider_api_env_var_name, printf, export.
  - is_valid_json_string: Valida la conformità sintattica JSON di una stringa.
    Input: $1 (stringa). Output: Stato 0 o 1. Dipendenze: printf, jq.
  - b64encode: Esegue la codifica Base64 a riga singola in modo portabile,
    tentando prioritariamente openssl enc. Input: stdin. Output: Stringa
    codificata su stdout. Dipendenze: openssl, base64, tr.
  - b64decode: Esegue la decodifica Base64 isolando flussi tramite awk (folding
    righe a 64 caratteri) per prevenire troncamenti anomali con LibreSSL/BSD.
    Input: stdin. Output: Flusso decodificato su stdout. Dipendenze: awk,
    openssl, base64.
  - file_size: Restituisce la dimensione del file in byte sfruttando le
    definizioni di piattaforma. Input: $1 (percorso). Output: Byte su stdout.
    Dipendenze: stat, printf.
  - is_valid_json_file: Valida l'esistenza e conformità JSON di un file. Input:
    $1 (percorso). Output: Stato 0 o 1. Dipendenze: jq.
  - stage_b64: Codifica Base64 transazionale di un payload testuale. Controlla
    che non ecceda $MAX_STAGE_BYTES (default 10MB), scrive in temp, acquisisce
    lock esclusivo e sposta a destinazione finale applicando chmod 600. Input:
    $1 (sorgente; se vuoto legge stdin), $2 (destinazione). Dipendenze: dirname,
    safe_mkdir, _tmpf, cat, rm, file_size, base64, tr, chmod, lock_exec, mv,
    log_error, log_info.
  - lock_exec: Esegue un comando sotto flock esclusivo o directory lock
    provvisorio atomico (lockdir) con controllo PID ed mtime per evitare

VARIABILI

  - BASH4LLM_ROTATE_HISTORY: Flag per attivare la rotazione dello storico (1
    o 0, default 0).
  - BASH4LLM_HISTORY_MAX_FILES: Numero massimo di file storici autorizzati
    (default 100).
  - BASH4LLM_HISTORY_MAX_BYTES: Peso cumulativo massimo dei file storici
    (default 104857600, equivalenti a 100MB).
  - BASH4LLM_HISTORY_KEEP_DAYS: Giorni massimi di conservazione dei file storici
    (default 90).
  - THREAD_CACHE_DIR: Cartella della cache temporanea dei thread attivi
    (localizzata sotto thread_cache/ nella directory di configurazione).
  - CONTENT: Prompt testuale primario dell'utente.
  - PROVIDER: Provider API attivo. Default "groq".
  - JSON_INPUT: Input JSON strutturato fornito dall'utente per definire
    direttamente i messaggi o le proprietà della richiesta.
  - THREAD_ID: Identificatore alfanumerico del thread di chat corrente,
    trasformato in hash anonimizzato SAFE_THREAD_ID per la persistenza del
    contesto.
  - SAFE_THREAD_ID: Identificatore anonimizzato crittograficamente in memoria
    (digest esadecimale SHA-256) per evitare di scrivere identificativi o PII su disco.
  - THREAD_WINDOW: Finestra massima di messaggi storici dal log NDJSON del
    thread da accodare come contesto della chat.
  - TEMPLATE: Nome del file di template da applicare per formattare il prompt.
  - BATCH_FILE: Percorso del file batch contenente prompt da elaborare in
    sequenza.
  - CHAT_MODE: Flag booleano (1 o 0, default 0) per attivare l'interfaccia
    interattiva TUI REPL da terminale.
  - SET_DEFAULT_MODEL: Modello da salvare come default persistente per il
    provider attivo.
  - REFRESH_MODELS: Flag per forzare l'aggiornamento della lista dei modelli da
    API (1 o 0, default 0).
  - LIST_MODELS: Flag per visualizzare a schermo l'elenco dei modelli
    disponibili.
  - FORCE_SAVE_MODE: Regola il salvataggio output su disco (save, nosave, o
    vuoto basato sulla soglia THRESHOLD).
  - OUT_PATH: Percorso personalizzato per l'archiviazione dei risultati.
  - SYSTEM_PROMPT: Prompt di sistema personalizzato per istruire il modello LLM.
  - TEMPERATURE / TURE: Valore numerico decimale che regola la temperatura di
    campionamento delle risposte (default 1.0). Sincronizzato con TURE.
  - MAX_TOKENS: Limite massimo di token generabili nella risposta
    (default 4096).
  - MODEL: Nome identificativo del modello LLM richiesto per l'elaborazione.
  - AUTO_POLICY: Politica per la selezione automatica del modello di fallback
    (default "preferred").
  - QUIET: Flag booleano (1 o 0, default 0) per inibire i log informativi.
  - DRY_RUN: Flag booleano (1 o 0, default 0) per simulare l'esecuzione
    escludendo chiamate di rete reali.
  - STREAM_MODE: Flag booleano (1 o 0, default 0) per attivare lo streaming dei
    token in tempo reale via SSE.
  - OUTPUT_MODE: Configura lo stile di visualizzazione dei risultati (text, raw,
    json, pretty). Default "text".
  - THRESHOLD: Soglia limite espressa in caratteri al di sopra della quale i
    risultati vengono salvati nello storico (default 1000).
  - MAX_RETRIES: Limite di tentativi di connessione per errori temporanei
    (default 1).
  - SUPPORTED_PROVIDERS: Elenco testuale dei provider supportati (default "groq
    gemini huggingface mistral").
  - CURL_BASE_OPTS: Array dei parametri base immutabili passati a curl
    (--silent, --show-error, --no-buffer, --max-time 120).
  - FALLBACK_PAYLOAD: Payload Base64 alternativo impostato da un hook di
    post-esecuzione in caso di fallimento della chiamata API principale.
  - BASH4LLM_EDGE_EMPTY: Flag booleano diagnostico (1 o 0) che segnala
    l'intercettazione di un caso limite di risposta vuota dall'API provider.
  - BASH4LLM_EDGE_REQ_ID: Identificativo della richiesta estratto dalla risposta
    dell'API per fini diagnostici.
  - BASH4LLM_EDGE_FINISH_REASON: Motivo di completamento (finish_reason)
    estratto dalla risposta dell'API.
  - BASH4LLM_EDGE_COMPLETION_TOKENS: Conteggio numerico dei token di
    completamento restituiti dall'API nell'oggetto usage.

    file di metadati dal disco invalidando la cache in memoria. Input: $1
    (thread_id). Output: Stato 0 o BASH4LLM_ERR_TMP. Dipendenze:
    thread_validate_id, lock_exec, _thread_delete_locked,
    thread_cache_invalidate, log_error, log_info, rm.
  - _thread_rename_locked: Aggiorna atomicamente il file di metadati di un
    thread per cambiarne il titolo visualizzato nell'interfaccia. Input: $1
    (file_meta), $2 (tmp_meta), $3 (thread_id), $4 (titolo), $5 (conteggio_msg),
    $6 (ultimo_ts). Output: Scrittura file di metadati aggiornato con chmod 600.
    Dipendenze: jq, mv, chmod.
  - thread_rename_core: Rinomina transazionalmente il titolo di un thread
    aggiornandone i metadati storici sotto lock esclusivo di storico. Input: $1
    (thread_id), $2 (nuovo titolo). Output: Stato 0 o BASH4LLM_ERR_TMP.
    Dipendenze: thread_validate_id, _tmpf, lock_exec, _thread_rename_locked,
    log_error, log_info, printf, tr, awk, wc, tail, jq, rm.
  - acquire_thread_lock: Acquisisce un lock di processo esclusivo non-bloccante
    sul thread attivo (tramite flock sul file descriptor 8) per prevenire
    scritture o modifiche simultanee da parte di istanze concorrenti. Input:
    Nessuno ($THREAD_ID). Output: Stato 0 se acquisito o dry-run, altrimenti 15
    (BASH4LLM_ERR_TMP). Side-effects: Apertura del fd 8 associato al file
    .concurrency.lock e lock esclusivo. Dipendenze: thread_validate_id,
    safe_mkdir, log_error, dirname, flock, exec.
  - release_thread_lock: Rilascia il lock di processo esclusivo del thread
    attivo chiudendo il file descriptor 8 associato. Input: Nessuno
    ($THREAD_ID). Output: Stato 0 o 15 se l'ID è invalido o il lockfile è
    symlink. Side-effects: Chiusura fd 8. Dipendenze: thread_validate_id,
    log_error, exec.
  - _thread_read_window_locked: Estrae l'ultima porzione del database NDJSON del
    thread senza effettuare scansioni complete dell'intero file, ottimizzando le
    prestazioni di lettura. Input: $1 (file_thread), $2 (numero righe n), $3
    (file temporaneo destinazione). Output: Righe estratte nel file temporaneo.
    Dipendenze: tail, cp.
  - thread_read_window: Estrae dal file log NDJSON del thread la finestra degli
    ultimi n messaggi registrati. Opera sotto lock esclusivo, preleva le righe
    via _thread_read_window_locked ed unifica in array JSON ordinato tramite
    pipeline jq nativa (con Try-Catch resiliente ad interruzioni). Aggiorna i
    metadati del thread in threads/.json via ui_state_write. Input: $1
    (thread_id), $2 (finestra messaggi, default 10), $3 (file JSON
    destinazione). Output: File JSON strutturato stampato in destinazione e
    metadati UI aggiornati. Stato 0 o 1. Dipendenze: thread_validate_id,
    safe_mkdir, _tmpf, lock_exec, _thread_read_window_locked, ui_state_write,
    ensure_run_tmpdir, log_error, log_warn, grep, chmod, jq, mv, cp, rm, wc,
    tail, printf.
  - thread_append: Accoda un nuovo messaggio nel registro NDJSON del thread.
    Genera un ID messaggio univoco (SHA-256), coordina la scrittura atomica
    tramite lock flock e previene conflitti verificando i marcatori di blocco
    del PID. Aggiorna i metadati del thread ed il relativo indice globale sotto
    lock esclusivo. Input: $1 (thread_id), $2 (ruolo: user/assistant/system), $3
    (testo), $4 (metadati JSON). Output: Messaggio aggiunto in append nel file
    NDJSON di storico con chmod 600. Metadati e indici JSON UI aggiornati.
    Stato 0 o 1. Dipendenze: thread_validate_id, thread_now_ts, safe_mkdir,
    _tmpf, ui_state_write, lock_exec, _update_thread_index, ensure_run_tmpdir,
    log_error, log_warn, log_info, jq, sed, awk, sha256sum, openssl, mkdir,
    printf, chmod, grep, flock, rmdir, wc, tail, touch.
  - _thread_hash: Genera un hash crittografico sicuro SHA-256 (con fallback su
    codifica Base64 troncata qualora non vi siano binari idonei installati) per
    identificare in modo univoco una stringa o combinazione di parametri. Input:
    $1 (stringa). Output: Stringa di hash su stdout. Dipendenze: sha256sum, awk,
    openssl, base64, tr, cut, printf.
  - thread_cache_key: Calcola la chiave identificativa univoca di cache
    accoppiando l'ID thread con l'hash SHA-256 dei parametri di invocazione
    forniti. Input: $1 (ID thread), $2 (stringa parametri). Output: Chiave su
    stdout (formato thread_id|hash_parametri). Dipendenze: _thread_hash, printf.
  - thread_cache_get: Estrae i risultati archiviati nella cache temporanea per
    il specifico thread e i parametri indicati. Verifica la validità temporale
    del record leggendone la prima riga (timestamp Unix di scadenza) e
    confrontandola con l'ora corrente; se scaduto, cancella fisicamente il file
    e restituisce un errore. Input: $1 (ID thread), $2 (stringa parametri), $3
    (opzionale: file destinazione). Output: Riversa i dati su stdout o scrive
    nel file se valida. Stato 0 (successo) o 1 (mancante/scaduta). Side-effects:
    Cancellazione file da disco se scaduto. Dipendenze: thread_cache_key, date,
    rm, tail, read.
  - thread_cache_set: Persiste i risultati di un thread e dei relativi parametri
    nella cartella di cache, impostando un tempo di validità personalizzato
    (TTL, default 300s). Scrive la scadenza Unix in riga 1, annette in coda i
    dati (da file o stdin) e archivia il file atomicamente con chmod 600. Input:
    $1 (ID thread), $2 (parametri), $3 (TTL in secondi, default 300), $4
    (opzionale: file sorgente; se assente legge stdin). Output: File di cache
    generato sotto $THREAD_CACHE_DIR. Stato 0 o 1. Dipendenze: thread_cache_key,
    _tmpf, date, cat, chmod, mv, rm.
  - thread_cache_invalidate: Invalida e purga i file di cache associati a una
    sessione thread. Se sono passati parametri specifici, elimina esclusivamente
    la cache di quella combinazione, altrimenti rimuove tutti i file di cache
    correlati all'ID della sessione. Input: $1 (ID thread), $2 (opzionale:
    parametri). Output: Cancellazione fisica file. Stato 0 o 1. Dipendenze:
    thread_cache_key, rm.
  - _normalize_bool_env: Uniforma i parametri di configurazione booleani
    principali presenti nell'ambiente (ALLOW_API_CALLS, DRY_RUN, DEBUG),
    convertendo stringhe permissive nei valori numerici 1 (attivo) o 0
    (inattivo) ed esportandoli. Input: Nessuno. Output: Esporta le variabili
    allineate. Dipendenze: is_truthy, declare, export.
  - _exec_curl_secure: Percorso autorevole ed unico per l'esecuzione di tutte le
    chiamate HTTP/cURL. Isola gli header sensibili contenenti i token Bearer
    all'interno di un file temporaneo con permessi 600 in $RUN_TMPDIR. Collega
    il file al file descriptor 3 e passa l'header a curl tramite redirezione
    /dev/fd/3 o /proc/self/fd/3, scollegando e rimuovendo immediatamente il
    file. Garantisce la totale inesistenza di secret o token Bearer negli
    argomenti di processo (argv), rendendoli invisibili a ps/top. Input: $1
    (metodo HTTP, default POST), $2 (URL API), $3 (chiave API), $4 (file
    payload), $5 (file output), $6 (file log errori), $7 (flag streaming 1/0),
    $8 (ref array opzioni cURL extra). Output: Restituisce lo stato HTTP o il
    codice di uscita di curl. Side-effects: Connessione di rete, allocazione e
    cancellazione file temporanei per header su fd 3, scrittura risposte e log.
    Dipendenze: _tmpf, printf, chmod, exec, curl, rm.

FUNZIONI

  - buildpayload_groq: Compila ed organizza la struttura del file JSON di
    payload da trasmettere all'endpoint delle API di Groq per le Chat
    Completions. Valida la correttezza numerica di TEMPERATURE (sincronizzata
    con TURE, default 1.0) e MAX_TOKENS (default 4096), impostando il flag
    booleano JSON per lo streaming (stream: true/false). Determina la sequenza
    di messaggi analizzando in priorità JSON_INPUT, MESSAGES_JSON,
    BUILD_MESSAGES_FILE o CONTENT. Se nessuna sorgente produce messaggi validi,
    genera come fallback un record utente con testo vuoto
    [{"role":"user","content":""}]. Inserisce SYSTEM_PROMPT se presente e
    imposta MODEL dal file dei messaggi se non definito. Scrive il JSON
    temporaneo via jq e, se la funzione stage_b64 è presente nel runtime, esegue
    lo staging Base64 transazionale (payload.json.b64) per garantire operazioni
    atomiche e protette. Input: Variabili d'ambiente di configurazione. Output:
    Assegna il percorso del file di payload finale a PAYLOAD ed esporta PAYLOAD.
    Ritorna stato 0 o BASH4LLM_ERR_TMP in caso di errori di scrittura.
    Side-effects: Creazione/rimozione file temporanei intermedi, eventuale
    staging Base64, scrittura log di avviso o debug su stderr. Dipendenze:

    is_valid_json_file, stage_b64, log_error, log_info, grep, jq, rm, wc, head,
    export.
  - call_api_groq: Esegue una richiesta API sincrona e non-streaming verso
    l'endpoint delle Chat Completions di Groq. Verifica la politica di rete via
    enforce_network_policy, risolve l'URL tramite BASH4LLM_PROVIDER_URL e
    decodifica il payload se codificato in Base64 (.b64). Invoca l'esecutore di
    rete blindato _exec_curl_secure passando metodo POST, URL, chiave API,
    payload decodificato e file temporanei per output e log di errore.
    _exec_curl_secure isola la chiave API e le intestazioni Bearer all'interno
    di un file temporaneo 600 inoltrato a curl tramite redirezione su file
    descriptor scollegato (/dev/fd/3), rendendola invisibile ai processi di
    sistema. Salva il risultato nel file RESP con
    permessi 600. Input: Nessuno (BASH4LLM_PROVIDER_URL, $GROQ_API_KEY,
    $PAYLOAD). Output: File di risposta salvato in $RESP. Ritorna stato 0,
    BASH4LLM_ERR_CURL_FAILED o BASH4LLM_ERR_API. Side-effects: Chiamata HTTP
    POST via _exec_curl_secure, decodifica payload Base64, allocazione/rimozione
    file temporanei, scrittura $RESP. Dipendenze: enforce_network_policy, _tmpf,
    b64decode, _exec_curl_secure, log_error, log_info, mv, cp, chmod, rm, cat.
  - call_api_streaming_groq: Esegue una chiamata API con risposta in tempo reale
    (streaming dei token via Server-Sent Events - SSE) verso l'endpoint di Groq.
    Verifica la politica di rete e accerta la presenza della chiave API.
    Decodifica il payload se Base64 ed isola le intestazioni Bearer in un file
    temporaneo 600 inoltrato su file descriptor 3. Invia la richiesta POST via
    _exec_curl_secure in unbuffered streaming (--http1.1 -sS -N). Collega
    l'output ad una pipeline con tee e jq unbuffered (jq --unbuffered -R -r),
    estraendo i delta di contenuto (.choices[0].delta.content) stampandoli
    all'istante su stdout e gestendo messaggi d'errore del server. Accumula le
    linee data: del flusso SSE in file provvisori, convalida i singoli blocchi
    JSON e ricostruisce la risposta JSON sintetica finale completa salvandola in
    $RESP con permessi 600. Scrive atomicamente i metadati dell'operazione in
    last_api.json. Input: Nessuno. Output: Flusso di token stampato su stdout,
    pacchetto JSON finale ricomposto e salvato in $RESP, stato cURL.
    Side-effects: Connessione di rete persistente, decodifica, output continuo
    su console, allocazione/rimozione file di staging SSE, aggiornamento atomico
    stato UI. Dipendenze: enforce_network_policy, _tmpf, b64decode,
    _exec_curl_secure, ui_state_write, log_error, log_info, ensure_run_tmpdir,
    jq, tee, grep, sed, mv, cp, chmod, rm, date.
  - refresh_models_groq: Sincronizza ed aggiorna la lista locale dei modelli
    supportati interrogando l'endpoint /openai/v1/models di Groq via GET
    autenticata tramite _exec_curl_secure. Valida che la risposta sia un JSON

    transazionale via b64_atomic_write e scrive il file $MODELS_FILE sotto lock
    esclusivo MODELS_LOCK con permessi 600. Input: Nessuno. Output: File
    $MODELS_FILE aggiornato e salvato su disco. Ritorna stato 0,
    BASH4LLM_ERR_NO_API_KEY, BASH4LLM_ERR_API o BASH4LLM_ERR_TMP. Side-effects:
    Chiamata GET HTTP, allocazione directory temporanea isolata,
    elaborazione/filtraggio stringhe, scrittura atomica con lock esclusivo su
    $MODELS_FILE. Dipendenze: ensure_run_tmpdir, resolve_provider_url,
    _exec_curl_secure, safe_mkdir, _mktemp_in_dir, _tmpf, b64_atomic_write,
    lock_exec, log_info_user, log_error, mktemp, rm, jq, awk, sed, sort, cat,
    base64, chmod.
  - validate_model_groq: Convalida la compatibilità del modello richiesto
    rispetto al file dei modelli locali di Groq e ai vincoli di I/O testuale

  - validate_key_groq: Diagnostica la validità della chiave API del provider

  - refresh_models_dispatch: Dispaccia l'aggiornamento dei moduli dei modelli al
    provider attivo (refresh_models_). Tenta con percorso file dest, fallback
    senza argomenti se firma incompatibile. Input: $1 (opzionale: file dest,
    default $MODELS_FILE). Output: Lista modelli aggiornata su disco, stato 0 o
    errore. Dipendenze: type, log_error, log_info, print_persistence_reminder.
  - validate_model_dispatch: Dispaccia la validazione sintattica e di
    compatibilità del modello al provider attivo (validate_model_). Se non
    supportata, emette un avviso ed esegue una convalida permissiva di fallback.
    Input: $1 (modello). Output: Stato uscita validatore o 0. Dipendenze: type,
    log_warn.
  - auto_select_model_dispatch: Dispaccia la selezione automatica del modello
    alla routine nativa del provider attivo (auto_select_model_). Input:
    Nessuno. Output: Nome modello su stdout e stato d'uscita. Dipendenze: type.
  - _lock_security_guards: Sigilla in sola lettura (readonly -f) le funzioni
    critiche di sicurezza e mediazione (_exec_curl_secure,
    verify_module_integrity, read_secure_input, validate_path_security,
    atomic_write, check_local_rate_limit, enforce_network_policy,
    execute_isolated_hook), impedendo monkey-patching durante l'esecuzione.
    Input: Nessuno. Output: Nessuno. Dipendenze: readonly.
  - resolve_model: Risolve ed assegna il modello LLM finale seguendo una
    gerarchia rigida: 1. CLI (-m/--model), 2. file canonico del provider
    (model.), 3. auto-selezione auto_select_model_dispatch, 4. scansione riga
    per riga di MODELS_FILE fino a $MAX_MODELS, 5. config globale, 6. whitelist
    $ALLOWED_MODELS. Input: Nessuno. Output: Stato 0 (assegna FINAL_MODEL) o 1
    in caso di fallimento. Side-effects: Letture file-system, validazione
    modelli. Dipendenze: canonical_model_file, canonical_provider_file,
    canonical_config_dir, validate_model_core, validate_model_dispatch,
    auto_select_model_dispatch, _normalize_model_name, is_supported_model,
    log_warn, log_error, sed, awk.
  - build_payload_from_vars: Dispaccia ed orchestra la costruzione del file JSON
    di richiesta API richiamando la routine del provider attivo (buildpayload_).
    Input: Nessuno. Output: File payload generato, stato 0 o errore
    BASH4LLM_ERR_API. Dipendenze: ensure_run_tmpdir, call_provider, log_error.
  - call_api_once: Dispaccia una singola chiamata API sincrona non-streaming via
    provider (call_api_). Se in dry-run, esclude la rete e mostra le prime righe
    del payload. Input: Nessuno. Output: Stato esecuzione o 0. Dipendenze:
    call_provider, show_payload_head, log_info, log_error.
  - call_api_streaming: Dispaccia la chiamata API in streaming via provider
    (call_api_streaming_) sotto lock di thread ed il controllo di rate limit
    locale. Ripristina in sicurezza SIGINT per sbloccare il lock del thread in
    caso di uscita abrupta. Se dry-run, simula e mostra la testa del payload.
    Input: Nessuno. Output: Stato esecuzione o 0. Side-effects: Lock thread,
    gestione segnali, connessione persistente. Dipendenze: acquire_thread_lock,
    release_thread_lock, check_local_rate_limit, call_provider,
    show_payload_head, log_info, log_error, trap, printf.
  - extract_api_error: Ispeziona ed estrae il messaggio d'errore formale dal
    file di risposta RESP (ispezionando campi JSON o prima riga di testo crudo).
    Input: Nessuno (RESP). Output: Messaggio errore su stdout. Dipendenze: jq,
    awk, head.
  - detect_empty_edge_case: Algoritmo diagnostico per intercettare risposte
    "vuote" anomale (HTTP 200 con finish_reason stop e token <= 1 ma prive di
    testo). Analizza RESP ed estrae request ID, finish reason e token. Input:
    Nessuno (RESP). Output: Assegna BASH4LLM_EDGE_EMPTY (0/1) e salva metadati in
    variabili globali. Dipendenze: _tmpf, is_valid_json_file, cp, jq, rm.
  - finalize_and_output: Formatta e visualizza i risultati secondo $OUTPUT_MODE
    (text, raw, json, pretty). Se il flag SANITIZE_OUTPUT è attivo, esegue la
    sanificazione ANSI/testo tramite output-sanitizer.sh o fallback POSIX nativo.
    Inoltre, ne gestisce il salvataggio atomico su disco se la dimensione supera
    $THRESHOLD o se richiesto (--save) sotto lock concorrenziale con umask 077.
    Input: $1 (formato), $2 (testo). Output: Output stampato, file archiviato se
    abilitato, stato 0 o BASH4LLM_ERR_TMP. Dipendenze: _tmpf, safe_mkdir,
    lock_exec, verify_module_integrity, is_truthy, log_error, log_warn, cp, cat,
    jq, printf, wc, tr, date, dirname, chmod.
  - validate_response_syntax: Esegue la validazione sintattica del testo estratto
    dalla risposta. Se VALIDATE_SML è attivo, verifica la conformità allo
    standard EBNF SML v2.0. Se VALIDATE_REGEX è definita, verifica che il testo
    soddisfi l'espressione regolare POSIX ERE fornita. Input: $1 (testo).
    Output: Stato 0 (valido) o 1 (fallito). Dipendenze: is_truthy, grep.
  - perform_request_once: Orchestra l'esecuzione complessiva di una richiesta
    sincrona sotto lock di thread: esegue gli hook isolati pre e post via
    execute_isolated_hook, verifica il rate limit locale (check_local_rate_limit),
    esegue la validazione sintattica della risposta (validate_response_syntax)
    ed esegue la chiamata con retry automatico per errori temporanei (fino a
    $MAX_RETRIES). Diagnostica casi vuoti, notifica errori API e registra i
    metadati in last_api.json. Input: Nessuno. Output: Output generato su
    console, stato 0, BASH4LLM_ERR_PARSE (13) o BASH4LLM_ERR_API. Dipendenze:
    acquire_thread_lock, release_thread_lock, execute_isolated_hook,
    check_local_rate_limit, call_api_once, extract_text_from_resp,
    validate_response_syntax, detect_empty_edge_case, ui_state_write,
    extract_api_error, finalize_and_output, log_info, log_error, log_warn,
    b64decode, trap, jq, head, sleep, printf.
  - collect_input_from_files: Legge e concatena i file di input passati con -f,
    validandone la sicurezza con validate_file_input ed inserendo delimitatori
    visivi. Input: Array percorsi ($@). Output: Testo unificato su stdout. Esce
    con BASH4LLM_ERR_SEC (17) se non sicuro. Dipendenze: file_readable,
    validate_file_input, log_error, cat.
  - expand_args_to_content: Converte gli argomenti posizionali CLI in prompt. Se
    un argomento è un file leggibile, ne valida la sicurezza via
    validate_file_input e ne legge il contenuto, altrimenti lo accoda come
    testo. Input: Array $ARGS. Output: Prompt unificato su stdout. Dipendenze:
    file_readable, validate_file_input, log_error, cat.
  - file_readable: Convalida se il percorso indica un file regolare
    effettivamente leggibile dall'utente corrente. Input: $1 (percorso). Output:
    Stato 0 o 1.
  - is_supported_model: Analizza il nome del modello e ne convalida la
    compatibilità, filtrando e scartando formati non-testuali (visione, audio,
    embedding, vettori, multimodali). Input: $1 (modello). Output: Stato 0
    (supportato) o 1. Dipendenze: tr.
  - list_models_cli: Formatta e visualizza su stderr l'elenco dei modelli locali
    normalizzandoli con _normalize_model_name, evidenziando quelli non
    supportati. Input: Nessuno ($MODELS_FILE). Output: Elenco su stderr, stato 0
    o 1. Dipendenze: _normalize_model_name, is_supported_model, printf.
  - validate_model_core: Algoritmo centrale di validazione modelli. Normalizza
    il nome via _normalize_model_name, controlla la presenza nel file locale e
    verifica la compatibilità con is_supported_model. Input: $1 (modello).
    Output: Stato 0 o 1. Dipendenze: _normalize_model_name, is_supported_model,
    grep, awk, printf.
  - load_local_config: Carica i parametri di configurazione dal file config
    sotto $BASH4LLM_CONFIG_DIR in memoria (MODEL, TEMPERATURE/TURE, MAX_TOKENS,
    FORMAT, THRESHOLD), ignorando commenti e pulendo gli spazi. Input: Nessuno.
    Output: Assegna variabili globali.
  - load_whitelist: Carica in memoria la lista dei modelli autorizzati da
    MODELS_FILE tramite _normalize_model_name per comporre la stringa
    $ALLOWED_MODELS. Input: Nessuno. Output: Assegna ALLOWED_MODELS. Dipendenze:
    _normalize_model_name.
  - is_tty_out: Verifica se stdout è collegato ad un terminale TTY reale. Input:
    Nessuno. Output: Stato 0 (TTY) o 1. Dipendenze: test [ -t 1 ].

BLOCCHI DI CODICE

  - CORE_SETUP_DISPATCH_HELPERS - Fase: Registrazione dispatch e blocco

  - CORE_SETUP_CLI_PARSE - Fase: Parsing argomenti riga di comando. - Azione:

  - CORE_SETUP_SESSION_ENGINE - Fase: Integrazione ed attivazione Session

  - CORE_SETUP_ACTIONS - Fase: Esecuzione comandi amministrativi ed offline. -
    Azione: Elabora ed esegue immediatamente comandi senza chiamate API:
    eliminazione/ ridenominazione thread, listati, impostazione default
    (--set-default), delega alla test suite master (--test), installazione
    estensioni (--install-extras) con permessi restrittivi (700/600) e verifica
    SHA-256 contro manifest.sha256, ed inizializzazione thread (--init-thread).

5.  CORE_PROVIDER

VARIABILI

  - _supported_providers_arr: Array interno utilizzato per la memorizzazione e
    l'indicizzazione dinamica di tutti i moduli provider rilevati ed installati
    nelle directory delle estensioni vendor e locali.
  - SUPPORTED_PROVIDERS: Elenco testuale unificato dei provider supportati
    separati da caratteri di spazio.
  - PROVIDER: Identificatore del provider attivo (sincronizzato con la selezione
    persistita nel file canonico del provider o sovrascritta tramite CLI/menu
    interattivo).
  - PROVIDER_INTERACTIVE_SELECTED: Flag booleano interno (valore 1 o 0) che
    attesta l'avvenuta selezione del provider tramite menu interattivo da
    terminale.
  - FINAL_MODEL: Nome del modello finale validato e risolto dalla routine
    resolve_model, pronto per l'invio nelle chiamate API.
  - STDIN_CONTENT: Buffer di memoria adibito alla memorizzazione del flusso di
    testo catturato dallo standard input (cat -) in caso di redirezioni o
    pipeline.

FUNZIONI

  - validate_provider_interface: Convalida che il modulo del provider attivo
    implementi correttamente le specifiche dell'interfaccia di Bash4LLM⁺.
    Verifica la presenza fisica in memoria delle funzioni obbligatorie
    (buildpayload_ e call_api_), e traccia a scopo informativo la presenza o
    assenza dei metodi opzionali (call_api_streaming_, refresh_models_,
    validate_model_, auto_select_model_). Input: $1 (nome identificativo del
    provider da analizzare). Output: Ritorna stato 0 se l'interfaccia
    obbligatoria è pienamente implementata, 1 in caso contrario (emettendo
    errori critici loggati via log_error). Side-effects: Scrittura di log di
    errore o informativi su stderr. Dipendenze: type, log_error, log_info.
  - assemble_content: Compila ed organizza la stringa del prompt di input
    principale $CONTENT che verrà inviata al modello LLM. Segue una catena di
    regole di priorità esclusive: 1. Se è configurato un JSON utente in
    $JSON_INPUT, pulisce la variabile CONTENT ed esce (in quanto il JSON di input
    definisce autonomamente i messaggi). 2. Se l'utente ha inserito dei file via
    parametro -f (FILE_INPUTS), ne raccoglie ed unifica i contenuti via
    collect_input_from_files (previa validazione di sicurezza validate_file_input).
    Se sono presenti argomenti posizionali aggiuntivi, li annette in coda come
    frammenti testuali. 3. Se è richiesto l'uso di un template ($TEMPLATE),
    preleva il file del modello dalla directory dei template, esegue la
    sostituzione della stringa segnaposto {{CONTENT}} rimpiazzandola con il
    prompt inserito (proveniente da file, da stdin o da argomenti posizionali)
    usando awk con file di staging intermedi temporanei, e assegna il testo
    risultante a CONTENT. 4. Se è presente dell'input catturato dallo standard
    input (STDIN_CONTENT), lo adotta come prompt principale, allegando in coda
    eventuali argomenti posizionali. 5. Se vi sono solo argomenti CLI posizionali
    in $ARGS, li converte ed unisce nel prompt testuale principale via
    expand_args_to_content. Input: Nessuno. Output: Stringa compilata assegnata
    alla variabile globale $CONTENT. Side-effects: Lettura file, generazione e
    distruzione di file di staging temporanei atomici sul disco tramite
    _mktemp_in_dir, sostituzione di stringhe via awk. Dipendenze:
    collect_input_from_files, expand_args_to_content, ensure_run_tmpdir,
    _mktemp_in_dir, cat, awk, mv, rm, printf.

BLOCCHI DI CODICE

  - CORE_PROVIDER_PRO_LOAD_INITIALIZATION - Fase: Selezione, persistenza e
    caricamento del modulo provider attivo. - Azione: Scansiona le directory dei
    provider esterni (vendor e local) per mappare i moduli installati. Determina
    il provider attivo leggendolo dai parametri CLI o dal file di configurazione
    canonico del provider PROVIDER_FILE (adottando "groq" in caso di assenza).
    Se configurato un nuovo provider da CLI (PROVIDER_CLI diverso da "list" e
    non interattivo): convalida l'appartenenza ai provider supportati, salva
    transazionalmente la scelta nel file $PROVIDER_FILE con permessi 600 via
    atomic_write, rimuove il vecchio file URL del provider e risolve il nuovo
    endpoint. Se richiesta la selezione interattiva (--provider senza argomenti o
    valore "list"): visualizza a schermo il menu numerato dei provider disponibili
    evidenziando il predefinito corrente, acquisisce la scelta dell'utente da
    stdin (accettando l'indice o il nome letterale e adottando il default se
    premuto invio), scrive in modo atomico la scelta in $PROVIDER_FILE con
    permessi 600 via atomic_write, rimuove il vecchio file URL del provider e
    risolve il nuovo URL. Se il provider attivo è "groq" e manca il file URL
    locale, scrive l'URL dell'API predefinito nel file canonico tramite
    write_provider_url_if_missing. Invoca la funzione di caricamento sicuro
    load_provider_module per importare le funzioni del modulo provider ed esegue
    la risoluzione dell'URL dell'API. Se l'interfaccia interattiva viene
    eseguita senza comandi aggiuntivi, stampa la conferma del provider impostato
    ed esce direttamente con stato 0.
  - CORE_PROVIDER_PRO_LOAD_VALIDATION_REFRESH - Fase: Validazione del modulo
    provider ed allineamento modelli. - Azione: Verifica che il modulo del
    provider sia stato correttamente importato ed esegue la convalida della
    conformità della sua interfaccia via validate_provider_interface; in caso di
    errori strutturali termina con codice BASH4LLM_ERR_API. Se è stato richiesto
    esplicitamente il refresh dei modelli ($REFRESH_MODELS attivo), richiede la
    chiave API ed avvia l'allineamento dei modelli locali tramite
    refresh_models_dispatch, terminando con stato 0. In subordine, se il file
    dei modelli locali $MODELS_FILE è assente o completamente vuoto, tenta di
    eseguire un allineamento automatico dei modelli in background (richiedendo
    la chiave API ed invocando la routine di refresh, senza interrompere lo
    script in caso di fallimento per permettere l'elaborazione dei flussi in
    background).
  - CORE_PROVIDER_SHOW - Fase: Esecuzione delle risposte diagnostiche immediate.
    - Azione: Gestisce e soddisfa le richieste diagnostiche e di ispezione dei
    percorsi dello script, terminando l'esecuzione con stato 0 dopo la
    visualizzazione dei dati: --print-config-dir / PRINT_CONFIG_DIR: Stampa il
    percorso della directory di configurazione canonica. --print-provider-file /
    PRINT_PROVIDER_FILE: Stampa il percorso del file canonico del provider.
    PRINT_MODEL_FILE: Stampa il percorso del file del modello canonico per il
    provider indicato. SHOW_CONFIG: Visualizza un riepilogo tabulare dettagliato
    dei parametri correnti dell'installazione (versione, date, provider attivo,
    modello attivo, temperatura, token massimi, formato output, soglia di
    salvataggio). DIAGNOSTICS: Esegue un'analisi di integrità diagnostica
    completa dello stato del sistema: scansiona e verifica l'esistenza e
    l'accessibilità fisica di tutte le directory operative, verifica lo stato
    del file di manifesto dell'integrità delle estensioni, controlla lo stato di
    abilitazione del Key Vault OpenSSL, lo stato di sblocco della sessione
    (_B4L_RT_CTX), il supporto PBKDF2, lo stato di inizializzazione del Vault ed
    esegue un test reale di TLS Handshake verso l'endpoint remoto attivo del
    provider via diagnose_tls_connection.
  - CORE_PROVIDER_MAIN_RESOLVE - Fase: Risoluzione del modello e cattura dello
    standard input. - Azione: Se l'avvio è per solo bootstrap ($BOOTSTRAP_ONLY
    attivo), esce immediatamente con stato 0. Carica le configurazioni locali
    via load_local_config e le whitelist dei modelli via load_whitelist,
    garantisce la stabilità della directory temporanea $RUN_TMPDIR, risolve il
    modello LLM finale da adottare via resolve_model ed esegue su di esso le
    convalide sintattiche e di interfaccia del provider (validate_model_core e
    validate_model_dispatch), terminando con codice BASH4LLM_ERR_BAD_MODEL se
    falliscono. Infine, cattura l'eventuale flusso di testo in arrivo da una
    redirezione o pipeline nello standard input (cat -) all'interno di
    STDIN_CONTENT e, in presenza di un JSON strutturato, ne estrae
    transazionalmente la chiave API interna ed i prompt d'ingresso
    sovrascrivendo e cancellando immediatamente il buffer per sicurezza.
  - CORE_PROVIDER_MAIN_EXECUTION - Fase: Esecuzione principale del prompt (Core
    Execution Loop). - Azione: Invoca assemble_content per generare il prompt
    definitivo. Se lo script è stato richiamato in modalità interattiva e non
    contiene prompt, visualizza la notifica del provider attivo ed esce. Esegue
    controlli di sicurezza sull'input bloccando l'esecuzione con codice
    BASH4LLM_ERR_NO_PROMPT in assenza di prompt testuale o JSON d'input (tranne
    se in chat interattiva, inizializzazione thread o elaborazione batch).
    Procede quindi con i tre flussi di esecuzione principali:
    1.  Elaborazione BATCH ($BATCH_FILE attivo): Scansiona il file batch riga
        per riga, escludendo righe vuote o commenti. Per ciascun prompt
        configura l'ambiente di thread se richiesto (validando l'ID thread,
        limitando la finestra dei messaggi, e richiamando
        session_engine_build_window o la legacy thread_read_window per compilare
        il JSON storico $BUILD_MESSAGES_FILE). Dispaccia la costruzione del
        payload via build_payload_from_vars, assicura la chiave API via
        ensure_api_key_for_provider ed avvia l'interrogazione dell'API (sincrona
        via perform_request_once o in streaming via call_api_streaming).
    2.  Chat Interattiva ($CHAT_MODE attivo): Trasferisce atomicamente
        l'esecuzione sostituendo l'immagine di processo dello script (exec bash)
        con l'utility esterna TUI REPL (tui-repl.sh) previa verifica di
        sicurezza del percorso e convalida dell'integrità crittografica SHA-256
        via verify_module_integrity.
    3.  Esecuzione Singolo Prompt (Streaming o Sincrona):
          - Se è definito un thread operativo ($THREAD_ID), esegue la
            validazione dell'ID, determina la finestra di recupero, e compila il
            file storico dei messaggi $BUILD_MESSAGES_FILE interrogando il
            Session Engine o richiamando la routine legacy di lettura NDJSON.
          - Compila il payload JSON via build_payload_from_vars.
          - Se si opera in esecuzione reale (non simulata DRY_RUN), valida e
            recupera la chiave API del provider via ensure_api_key_for_provider.
          - Se Streaming attivo ($STREAM_MODE == 1): Invoca la funzione di
            streaming dedicata (call_api_streaming) sotto lock esclusivo di
            thread. Se completato con successo, e non in modalità simulata
            DRY_RUN, sanifica ed accoda il messaggio dell'utente ed il testo
            restituito dall'assistente nel registro NDJSON del thread (delegando
            al Session Engine o alla legacy thread_append). Stampa un carattere
            a capo ed esce con stato 0.
          - Se Sincrono standard ($STREAM_MODE == 0): Stampa i dettagli
            diagnostici di visualizzazione del prompt e del modello se in
            terminale TTY interattivo verboso. Invoca la chiamata transazionale
            via perform_request_once sotto lock esclusivo di thread. In caso di
            successo, formatta l'output via finalize_and_output, registra
            l'interazione utente ed assistente nel file NDJSON del thread ed
            esce con stato 0. In caso di fallimento della chiamata, accoda
            comunque il messaggio utente al thread registrandolo come operazione
            fallita ed interrompe l'esecuzione restituendo lo stato d'uscita
            della perform_request_once.
