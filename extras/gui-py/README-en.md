## 1. Project Overview & Architectural Philosophy

### Application Purpose
The **`gui-py`** module is an optional, lightweight, high-performance web user interface designed to extend the **`bash4llm`** core script (v2.8.5+). Its primary purpose is to provide a modern graphical user experience (WebUI Single Page Application) accessible from any web browser, while preserving the deterministic and Bash-first nature of the underlying infrastructure.

### Key Architectural Principles

1. ***Thin Adapter* Model**:
   * The `bash4llm` core script remains the sole authority for domain logic, NDJSON conversation thread state, filesystem persistence, Vault encryption, provider selection, and direct API calls to LLMs.
   * The Python Adapter implements no domain storage of its own, does not alter file formats, and does not duplicate business logic.
   * The presence or absence of the `gui-py` module (or Python dependencies such as `fastapi`, `uvicorn`, `pydantic`) **does not modify or compromise in any way the operation of the `bash4llm` core script**.

2. ***Domain-Stateless / Runtime-Stateful***:
   * **Domain-Stateless**: The Python Adapter does not permanently store messages, API keys, or history. Thread reading occurs via read-only extraction from the `.ndjson` files generated by the core.
   * **Runtime-Stateful**: The Adapter manages in ephemeral RAM memory an active Job registry (`jobs_registry`), subprocess handlers (`process_pid`), Server-Sent Events token queues (`job_queues`), active client sessions (`sessions`), and a temporary idempotency table (`idempotency_store`).

3. ***Zero Credential Mirroring***:
   * Python does not store, extract, or manipulate LLM credentials or the Vault master password.
   * Call execution occurs by entirely delegating authentication to the `bash4llm` core via process environment variables or via the native Vault mechanism of the Bash script.

4. ***No Double Locking***:
   * The Python Adapter does not apply mutexes or synchronization locks to domain files. If two or more requests hit the same `thread_id` simultaneously, Python allocates and executes their respective asynchronous subprocesses, delegating transactional arbitration on the filesystem to the native atomic locking mechanism of `bash4llm` (`acquire_thread_lock`).

## 📋 2. User Guide (README & Quickstart)

### System Prerequisites
* **Shell & Core Utilities**: Bash >= 4.0, `curl`, `jq`, `mktemp`, `stat`, `base64`, `awk`, `sed`, `grep`.
* **Python Interpreter**: Python >= 3.10.
* **Required Python Libraries**: `fastapi`, `uvicorn`, `pydantic`.
* **Prohibition of Automation**: The launcher script does not automatically install packages nor create virtualenvs without explicit authorization. In case of missing dependencies, startup aborts providing exact instructions for manual installation.

### Installation and Synchronization
All module sources reside in the `extras/gui-py/` directory of the repository. Installation on the local system occurs via the core CLI:

```bash
./bash4llm --install-extras
```

This command copies the directory tree to `bash4llm.d/extras/gui-py/` applying restrictive permissions `0700` for directories and `0600` for files (Principle of Least Privilege).

### 🚀 Application Quickstart

Starting the WebApp GUI occurs directly via the `bash4llm` CLI:

```bash
./bash4llm --gui
# oppure
./bash4llm --graphic
```

The core script verifies the cryptographic integrity of the module via `manifest.sha256` and delegates execution to the wrapper script `extras/gui-py/gui-py.sh`.

#### 💻 Platform-by-Platform Execution

* **Linux / macOS**:
  ```bash
  ./bash4llm --gui
  ```
  The launcher script validates the Python environment, acquires the process Advisory Lock on `gui_adapter.lock` via `fcntl.flock`, allocates the first free loopback port (starting from `19970`), and automatically opens the authentication URL in the default browser via `webbrowser.open()`.

* **Windows (Git Bash / MSYS2)**:
  ```bash
  ./bash4llm --gui
  ```
  The script detects the Windows environment, manages the Advisory Lock via `msvcrt.locking` with a 1-byte initialization, and validates that the runtime temporary directory resides within the user profile (`USERPROFILE` / `LOCALAPPDATA`).

* **Android (Termux)**:
  ```bash
  ./bash4llm --gui
  ```
  Uses the `termux-open-url` utility to launch the system browser and leverages the JS client auto-reconnection logic in case of process suspension by the operating system (Doze Mode).

### 🌐 WebApp GUI User Manual

1. **Initial Authentication**: Upon startup, a single-use `one_time_token` is generated. The browser is directed to `http://127.0.0.1:19970/auth?one_time_token=...`. The token is consumed atomically in RAM and a secure `HttpOnly` session cookie is issued with the `SameSite=Strict` flag.
2. **Thread Navigation (Sidebar)**:
   * Clicking on **"+ New Thread"**, a new conversation context is created.
   * The sidebar displays all available threads read from the Read-Model. Selecting a thread loads the message history in read-only mode.
3. **Prompt Submission and Streaming**:
   * Enter text into the bottom text field and press **"Send"** (or submit via keyboard).
   * The LLM response is received in real time token-by-token via Server-Sent Events (SSE) streaming.
4. **Canceling In-Progress Job**: During response generation, the submit button transforms into the red **"Stop"** button. Clicking on it, the Adapter sends an interruption signal `POST /api/jobs/{id}/cancel` to the Bash subprocess, immediately stopping execution without corrupting pre-existing history.
5. **Settings Panel (Settings)**:
   * Clicking on **"Settings"**, it is possible to select the active Provider, Model, Temperature, and history window size (`thread_window`).

### Job Lifecycle (`JobState`)

Every generation request sent to the WebApp is encapsulated in a `Job` object managed in RAM memory by the Python Adapter.

```
       [ Client POST /api/chat ]
                   │
                   ▼
              ┌─────────┐
              │ CREATED │ (Allocato in memory registry)
              └────┬────┘
                   │
                   ▼
             ┌──────────┐
             │ STARTING │ (Invocazione subprocess asyncio)
             └─────┬────┘
                   │
                   ▼
              ┌─────────┐
              │ RUNNING │ (Iniezione prompt via stdin pipe)
              └────┬────┘
                   │
                   ▼
             ┌───────────┐
             │ STREAMING │ (Flussaggio token via SSE)
             └─────┬─────┘
                   │
     ┌─────────────┼───────────────────────────┐
     │             │                           │
     ▼             ▼                           ▼
┌───────────┐ ┌──────────┐            ┌──────────────────┐
│ COMPLETED │ │  FAILED  │            │ CANCEL_REQUESTED │
└───────────┘ └──────────┘            └────────┬─────────┘
(Exit Code 0) (Exit Code != 0                   │
               o errore JSON)         ┌─────────┴─────────┐
                                      │  Process Killed   │
                                      └─────────┬─────────┘
                                                │
                                                ▼
                                         ┌───────────┐
                                         │ CANCELLED │
                                         └───────────┘
```

#### Formal Description of States (`JobState` Enum)
* **`CREATED`**: The Job has been allocated in the idempotency registry `jobs_registry` with a unique `job_id` (`job_<hex16>`).
* **`STARTING`**: The Adapter has prepared the explicit list of CLI arguments and the sanitized environment, and is starting the subprocess via `asyncio.create_subprocess_exec`.
* **`RUNNING`**: The `bash4llm` process is active (`process.pid` assigned). The user prompt is sent via asynchronous write to the `stdin` pipe.
* **`STREAMING`**: The tokens generated by `bash4llm` are read from `stdout` via `codecs.getincrementaldecoder('utf-8')` and transmitted to the client via SSE.
* **`CANCEL_REQUESTED`**: A `POST /api/jobs/{job_id}/cancel` request was received. The Adapter has initiated the process tree termination procedure.
* **`CANCELLED`**: The `bash4llm` process was successfully terminated by a system signal (`SIGTERM` or `SIGKILL`). The `termination_cause` field is populated.
* **`COMPLETED`**: The `bash4llm` process exited spontaneously with exit code `0`. The complete response is stored in the `prompt_response` RAM buffer.
* **`FAILED`**: The process exited with a non-zero exit code or the core emitted a JSON diagnostic error on `stderr` (`core_error_code` $10\div17$).

### Multi-Tab & Active Clients Management

The Adapter manages the simultaneous presence of multiple connected tabs or browsers via dynamic session tracking.

#### Formal Definition of Active Client
A client is considered **Active** if at least one of the following conditions is met:
1. It has an open and listening HTTP Server-Sent Events stream (`/api/stream/{job_id}`).
2. It performed an HTTP interaction or sent a Heartbeat signal (`POST /api/heartbeat`) in the last $10.0$ seconds (`sessions[session_id] >= now - 10.0`).

#### Automatic Shutdown Algorithm (*Graceful Shutdown*)
To prevent the Python server from running indefinitely in the background when the browser is closed, the Adapter executes a permanent asynchronous task (`graceful_shutdown_checker`).

The server automatically shuts down by sending a `SIGINT` signal to itself if and only if the following logical-temporal equation is satisfied:

$$\text{server\_has\_seen\_first\_client} == \text{True} \quad \land \quad \text{Active Clients} == 0 \quad \land \quad \text{Active Jobs} == 0 \quad \land \quad (\text{now} - \text{grace\_started\_at}) \ge 15.0\text{s}$$

*Engineering Note*: The `server_has_seen_first_client` flag prevents early server shutdown during the startup phase (bootstrap), guaranteeing the user the necessary time to complete the initial authentication redirect.

### Subprocess Management and Cross-Platform Cleanup

Canceling a Job (`cancel_job_process`) is a deterministic process interruption and **not a transactional rollback**. If the core has already committed an NDJSON line before receiving the signal, the line remains authoritative in the domain.

#### Process Tree Termination Algorithm
1. **POSIX Platforms (Linux, macOS, WSL, Termux)**:
   * The Adapter sends the `signal.SIGTERM` signal to the subprocess PID (`os.kill(job.process_pid, signal.SIGTERM)`).
   * The Adapter sets `job.termination_cause = TerminationCause.SIGTERM` and waits in a non-blocking loop up to a maximum of $5.0$ seconds (`CANCELLATION_TERMINATION_TIMEOUT`).
   * If the process does not stop within $5.0$ seconds, the Adapter forces termination by sending `signal.SIGKILL` and updates `job.termination_cause = TerminationCause.SIGKILL`.

2. **Windows Platforms (Git Bash / MSYS2)**:
   * The Adapter asynchronously executes the native system utility:
     ```cmd
     taskkill /F /T /PID <process_pid>
     ```
   * This guarantees the forced and recursive termination of the entire child process tree spawned by the Bash shell.

## 4. IPC Protocol and Data Streaming (IPC Contract)

### Asynchronous CLI Invocation and Prompt Injection
The Python Adapter invokes the `bash4llm` core script, always enabling streaming mode and structured JSON diagnostics:

```python
cmd = [
    "bash", core_script_path,
    "--thread", job.thread_id,
    "--thread-window", str(job.thread_window),
    "--stream",
    "--json-diagnostics"
]
```

#### Passing the Prompt via `stdin` Pipe
To prevent security risks related to process inspection by other system users (`ps aux`) and overcome CLI argument length limits (`ARG_MAX`), the user prompt is injected exclusively via the `stdin` pipe:

```python
process = await asyncio.create_subprocess_exec(
    *cmd,
    stdin=asyncio.subprocess.PIPE,
    stdout=asyncio.subprocess.PIPE,
    stderr=asyncio.subprocess.PIPE,
    env=sanitized_env,
    cwd=runtime_dir
)

# Scrittura asincrona e chiusura atomica della pipe per inviare l'EOF
if process.stdin:
    process.stdin.write(job.prompt.encode('utf-8'))
    await process.stdin.drain()
    process.stdin.close()
```

### UTF-8 Decoding and OS Pipe Deadlock Prevention
To avoid subprocess blocking caused by OS pipe buffer saturation (OS Pipe Deadlock), `stdout` and `stderr` pipes are read concurrently via `asyncio.gather()`:

1. **`stdout` Reading and SSE Streaming**:
   Tokens emitted by the core are decoded progressively using an incremental UTF-8 decoder (`codecs.getincrementaldecoder('utf-8')(errors='replace')`), accumulated in the Job's RAM memory buffer, and instantly transmitted to the client's SSE queue:
   ```text
   id: 1
   event: token
   data: {"delta": "Ciao"}

   id: 2
   event: token
   data: {"delta": "!"}
   ```

2. **`stderr` Reading and Diagnostic Parsing (Zero Regex)**:
   Error diagnostics rely **exclusively** on parsing valid JSON lines emitted by `bash4llm` via the `emit_json_diagnostics` function. Any use of heuristic regular expressions on free text to infer core errors is strictly prohibited:
   ```json
   {"bash4llm_status":"ERROR","code":10,"reason":"NO_API_KEY","message":"GROQ_API_KEY is not set","timestamp":"2026-08-10T17:00:00Z"}
   ```

### 2-Level NDJSON Resolution (`GET /api/threads/{id}`)
To serve conversation message history without executing subprocess overhead, the Adapter applies high-performance **Read-Only** reading across two levels:

1. **Syntactic Validation**: Conversation ID verified via regex `^[A-Za-z0-9._-]{1,128}$`.
2. **Level 1 Lookup (SHA-256 Digest)**: Calculation of the native hash `sha256_hex = hashlib.sha256(thread_id.encode('utf-8')).hexdigest()`. Attempts opening the file:
   $$\text{bash4llm.d/history/threads/}\{\text{sha256\_hex}\}\text{.ndjson}$$
3. **Level 2 Lookup (Backward-Compatible Fallback)**: If the above file does not exist, attempts opening the file with plaintext ID:
   $$\text{bash4llm.d/history/threads/}\{\text{thread\_id}\}\text{.ndjson}$$
4. If neither file exists, the Adapter returns an empty array `[]`.

### Handling of `ui_state/last_api.json`
Files under the `ui_state/` directory represent a **non-transactional derived Read-Model** (*Best-Effort Non-Transactional Projection*, Invariant 9). The Adapter binds metadata from the last API call (HTTP status, `finish_reason` completion cause, request ID) to the Job object. In case of temporal discrepancies or concurrency, such metadata are marked `"metadata_verified": false` or omitted.

### Thread Index Reconstruction (Invariant 10)
If the index file `ui_state/threads/index.json` is missing or syntactically corrupt/invalid:
1. The Adapter performs a read-only scan of filenames alone in the `history/threads/*.ndjson` directory.
2. For each identified thread, the Adapter invokes the core CLI:
   ```bash
   bash4llm --init-thread --thread <thread_id>
   ```
3. The Adapter delegates atomic index regeneration on the filesystem solely to the Bash core.

## 5. Security Model and Route Protection

### Tree Security Architecture

```
[Richiesta HTTP GET / o POST /api/chat]
        │
        ├── 1. Host Validation (Allowlist: 127.0.0.1, localhost, [::1])
        │
        ├── 2. Primary Origin Validation (Origin deve corrispondere a [http://127.0.0.1](http://127.0.0.1):PORT)
        │
        ├── 3. Session Cookie Check (Cookie HttpOnly: session_id)
        │        │
        │        ├── Assente/Invalido su GET / o GET /index.html ──> Return HTTP 401 (error.html)
        │        └── Assente/Invalido su API Mutative ───────────> Return HTTP 401 (JSON)
        │
        ├── 4. Anti-CSRF Token Header Check (X-CSRF-Token per POST, PATCH, DELETE)
        │
        ├── 5. Job Ownership Check (Proprietà legata a owner_session_id)
        │
        └── 6. Fingerprinted Ephemeral Idempotency Check (SHA-256 Payload Fingerprint)
                 ├── Key preesistente + Stesso Fingerprint SHA-256 ──> Return 202 Accepted (Job esistente)
                 ├── Key preesistente + Fingerprint DIVERSO ──────────> Return HTTP 409 Conflict
                 └── Nuova Key ───────────────────────────────────────> Alloca ed esegue nuovo Job
```

### Specific Protection Mechanisms

* **Exclusive Loopback Binding**: The Uvicorn server is bound exclusively to local loopback addresses (`127.0.0.1` or `[::1]`). Binding to `0.0.0.0` is strictly prohibited.
* **Route and HTML Protection**:
  * Middleware intercepts requests to `/` and `/index.html`.
  * If the request lacks a valid `session_id` session cookie, the server rejects access with `HTTP 401 Unauthorized` serving the minimal error template `static/error.html`.
* **Single-Instance Advisory Lock**:
  * **POSIX**: `fcntl.flock(fd, fcntl.LOCK_EX | fcntl.LOCK_NB)` on file `gui_adapter.lock`.
  * **Windows**: `msvcrt.locking(fd, msvcrt.LK_NBLCK, 1)` after writing an initial byte to the file.
  * The OS kernel automatically releases the lock upon process closure or crash, eliminating the risk of stale lock files.
* **Cookie & Anti-CSRF**:
  * Session cookie: `Set-Cookie: session_id=...; HttpOnly; SameSite=Strict; Path=/`.
  * CSRF Token: Generated in RAM (`secrets.token_hex(32)`), returned in the payload of `/api/status`, and required in the `X-CSRF-Token` header for all mutative operations (`POST`, `PATCH`, `DELETE`).
* **Single-Use Bootstrap Token**:
  * Upon startup, `active_one_time_token = secrets.token_hex(32)` is generated.
  * The `/auth?one_time_token=XYZ` endpoint validates the token, consumes it atomically (setting it to `None` in RAM to prevent reuse), issues the session cookie, and performs an `HTTP 302 Redirect` to root `/`.

### Semantics of HTTP 202 Accepted Outcome
The `HTTP 202 Accepted` response returned by the `POST /api/chat` endpoint indicates solely that the request has been syntactically validated and the `Job` object has been **allocated in the Adapter's runtime**. Any execution errors from the Bash script or the remote API (error codes $10\div17$) are conveyed asynchronously inside the SSE stream and in the Job object queryable via `GET /api/jobs/{id}`.

### Mobile & Termux Resilience (Android Doze Mode)

On mobile devices based on Android/Termux, power-saving mechanisms (*Doze Mode*) or aggressive OEM policies may temporarily suspend the browser process or interrupt the SSE socket TCP connection.

To ensure maximum resilience:
1. **Independent Asynchronous Pipelining**: The Bash subprocess continues execution and token writing to the NDJSON file even if the web client disconnects from the SSE stream (Invariant 4).
2. **Auto-Reconnect EventSource**: The Vanilla JavaScript client (`app.js`) handles the `eventSource.onerror` error handler. In case of disconnection, the client attempts automatic reconnection to `/api/stream/{job_id}`.
3. **SSE Heartbeat Flushing**: The asynchronous generator of the `/api/stream/{job_id}` endpoint sends a heartbeat comment (`: heartbeat\n\n`) every 15 seconds of inactivity to prevent socket closure by network middleboxes or mobile-data gateways.
